>*"大任务拆小，每个小任务拿到干净上下文"* -- Subagent 用独立 messages[] 跑自己的循环，中间过程不污染主对话。
>
>**Harness 层**: 子 Agent — 上下文隔离，注意力不漂移。

## 问题

Agent 在修一个 bug。它读了 30 个文件来追踪调用链，中间聊了 60 轮。messages 列表涨到 120 条，其中大部分是"追踪调用链"的中间过程，和"修 bug"这个最终目标无关。

这些中间过程占着上下文位置，让 Agent 越来越"健忘"——它记不住最初的问题是什么了。s05 的 todo_write 能帮 Agent 记住"该做什么"，但它解决不了"上下文被中间过程淹没"的问题。

换个角度：你修 bug 的时候，会"开一个新终端"来追踪调用链。追踪完了，终端关掉，结果写进笔记，回到原来的终端继续修 bug。Agent 也需要这个能力：开一个独立的子进程，给它一个独立的消息列表，让它专心做一件事，做完只把结论带回来。

## 解决方案

```
  Parent Agent / 父智能体                 Subagent / 子智能体
  +------------------+                  +------------------+
  | messages=[...]   |                  | messages=[task]  | <-- fresh / 全新
  |                  |   dispatch       |                  |
  | tool: task       | ---------------> | own while loop   |
  |   prompt="..."   |                  |   bash/read/...  |
  |                  |   summary only   |   (max 30 turns) |
  | result = "..."   | <--------------- | return last text |
  +------------------+                  +------------------+
        ^                                      |
        |       intermediate results DISCARDED  |
        +--------------------------------------+
```

s05 的钩子结构和 `todo_write` 完全保留。新增的是一个 `task` 工具——调用时 spawn 一个子 Agent，拥有全新的 `messages[]`，跑自己的循环，结束后只把摘要文本回传给父 Agent。对话上下文被丢弃，但文件系统的副作用（写文件、改文件、跑命令）保留在工作目录中。

三大安全设计：
- **上下文隔离**：子 Agent 用 `messages=[task]`，中间过程不回传，父上下文不被污染
- **轮数限制**：`range(30)` 硬限制，防止子 Agent 无限循环
- **禁止递归**：`SUB_TOOLS` 不含 task，子 Agent 不能再派生子 Agent

```python
s06_subagent.py - 子智能体（Subagent）

s05 让 Agent 会规划了。但如果一个子任务本身就很复杂——"追踪 auth 模块的完整调用链"——
这件事产生的中间上下文不应该堆在主对话里。s06 的回答：派生子 Agent，给它们独立上下文。

    # 子 Agent 有自己的工具集：只有 5 个基础工具，没有 task（禁止递归）
    SUB_TOOLS = [bash, read_file, write_file, edit_file, glob]
    SUB_HANDLERS = {"bash": run_bash, "read_file": run_read, ...}

    def spawn_subagent(description: str) -> str:
        """派生一个子智能体，拥有全新 messages[]，仅返回最终摘要。"""
        print(f"[Subagent spawned]")
        messages = [{"role": "user", "content": description}]  # 全新上下文

        for _ in range(30):  # 安全限制：最多 30 轮
            response = client.messages.create(
                model=MODEL, system=SUB_SYSTEM,   # 子 Agent 有独立系统提示
                messages=messages, tools=SUB_TOOLS, max_tokens=8000,
            )
            messages.append({"role": "assistant", "content": response.content})
            if response.stop_reason != "tool_use":
                break

            # 子 Agent 也走钩子系统 —— 权限检查不因上下文隔离而跳过
            for block in response.content:
                if block.type == "tool_use":
                    blocked = trigger_hooks("PreToolUse", block)
                    if blocked:
                        results.append({... "content": str(blocked)})
                        continue
                    handler = SUB_HANDLERS.get(block.name)
                    output = handler(**block.input)
                    trigger_hooks("PostToolUse", block, output)
                    # 子 Agent 输出用灰色 [sub] 标记
                    print(f"  [sub] {block.name}: {str(output)[:100]}")

        print(f"[Subagent done]")
        return extract_text(messages[-1]["content"])  # 只回传结论

    # 主 Agent 把 task 当成普通工具用
    TOOLS.append({"name": "task", ...})
    TOOL_HANDLERS["task"] = spawn_subagent

dispatch 机制完全不变。task 工具通过 TOOL_HANDLERS[block.name] 分发，父循环不感知
子 Agent 的内部细节。父 Agent 的 agent_loop 和 s05 几乎一样——唯一的区别是 TOOLS
里多了一个 task 工具，TOOL_HANDLERS 里多了一行映射。

关键洞察：子 Agent 的 messages[] 跑完后完全丢弃，但文件系统的副作用保留。
读文件、写文件、跑 bash——这些都发生在 WORKDIR 里，父 Agent 可以直接看到结果。
上下文隔离的是"对话"，不是"后果"。
```

## 核心设计模式解读

1. **为什么要区分"对话上下文"和"文件系统副作用"？**
   子 Agent 追踪调用链的过程中，会读 30 个文件、grep 十几条命令。这些命令的输出堆积在 messages 里，淹没了真正重要的信息。但文件系统的改变（比如子 Agent 写的 `call_chain.txt`）是持久化到磁盘的，父 Agent 用 `read_file` 就能读到。上下文隔离的是"中间推理过程"，保留的是"最终产出物"。这个区分让 Agent 在不丢失信息的前提下，保持注意力集中。

2. **为什么子 Agent 不给 task 工具？—— 递归控制的简洁方案**
   不必设计复杂的调用栈追踪或深度计数器。`SUB_TOOLS` 就是 `TOOLS` 去掉 `task` 和 `todo_write`。子 Agent 能读写文件、跑命令，但不能喊帮手。这和一个"只干活不分派"的执行者角色完全吻合：老板（父 Agent）分派任务，执行者（子 Agent）自己干，不往下再分。生产环境（CC）的递归保护更精细——不是靠缺工具来实现的，而是用 `isInForkChild()` 检查对话历史中的 boilerplate tag——但"子 Agent 权限受限"这个核心理念是一致的。

3. **钩子系统在父子间的复用**
   子 Agent 在 `spawn_subagent` 内部也调用 `trigger_hooks("PreToolUse", block)`——这意味着 `permission_hook` 和 `log_hook` 同样作用于子 Agent 的工具调用。上下文隔离不代表权限隔离。如果父 Agent 受 `DENY_LIST` 保护，子 Agent 也受保护。钩子系统的设计在 s06 得到了验证：一次注册，父子共享。

4. **s05 的 dispatch map 模式第三次得到验证**
   s02 说"加工具不需要改循环"，s05 用 `todo_write` 证明了一次，s06 用 `task` 再证一次。而且这次更极端——`task` 的 handler 函数内部跑了一整个 `agent_loop`，是"自己调用自己"的模式。但因为 dispatch map 把接口统一为 `handler(**block.input) -> str`，父循环根本不关心 handler 内部做了什么。加一个能派生 Agent 的工具 = TOOLS 加 1 条定义 + TOOL_HANDLERS 加 1 行映射。循环不动。

5. **30 轮安全限制和兜底提取**
   子 Agent 的 `for _ in range(30)` 不仅是防御性编程，它决定了子 Agent 的"专注度"。30 轮足够追踪一个调用链或修改几个文件，但不够展开一个全新的重构项目。这个限制本身就是对子 Agent 职责范围的约束：你是来做一件事的，不是来开新项目的。安全兜底（轮数耗尽后向前查找助理文本）确保即使子 Agent 被截断，父 Agent 也能拿到一些有用的结论，不会空手而归。
