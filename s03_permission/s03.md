>*"安全不能靠信任模型，要靠代码"* -- 三道闸门插在工具执行前，循环只加了一行。
>
>**Harness 层**: 权限 -- 在工具执行前做判断。

## 问题

s02 的 Agent 有 5 个工具。file tools 受 `safe_path` 保护，但 bash 不受限制。让它"清理一下项目"，可能执行 `rm -rf /`。

更根本的问题是：s01 和 s02 的 `run_bash` 里虽然有一个 `dangerous` 列表，但它嵌在工具实现内部，和其他工具的权限逻辑是分离的。每次加新工具、新规则，安全代码会散落各处。

安全不能靠信任模型，要靠代码——在工具执行之前做统一的权限判断。

## 解决方案

```
+-------+    +--------+    +--------+    +--------+    +------+
| Tool  | -> | Gate 1 | -> | Gate 2 | -> | Gate 3 | -> | Exec |
| call  |    | deny?  |    | match? |    | allow? |    |      |
+-------+    +--------+    +--------+    +--------+    +------+
     |            |             |             |
     v            v             v             v
  (正常放行)   (直接拦截)    (询问用户)   (用户拒绝?)
```

s02 的循环完全保留。唯一的变动在工具执行前插入 `check_permission()`——每个工具调用经过三道闸门，顺序固定：硬拒绝优先，软询问次之，都没命中就放行。

```python
s03_permission.py - 权限系统（Permission System）

在 s01/s02 的 agent_loop 里，工具是"拿来就执行"的。
s03 在工具执行前插入了一道权限管线（Permission Pipeline）：

    for block in response.content:
        if block.type != "tool_use":
            continue
        
        # s03 新增：执行前通过三道门权限管道
        if not check_permission(block):    # ← 循环只加了这一行
            results.append({... "content": "Permission denied."})
            continue
        
        # 以下和 s02 完全一样
        output = TOOL_HANDLERS[block.name](**block.input)
        results.append(...)

三道闸门的分工：

    Gate 1: 硬拒绝列表（DENY_LIST）
        → 匹配即拦截，永不执行。rm -rf /、sudo、mkfs 等。
        → 原来嵌在 run_bash 里的 dangerous 列表上移到这里，职责清晰。

    Gate 2: 规则匹配（PERMISSION_RULES）
        → 上下文判断。写工作区外？bash 命令含 rm？
        → 每条规则指定目标工具 + 检查条件 + 告警信息。
        → 命中后不直接拒绝，交给 Gate 3。

    Gate 3: 用户审批（ask_user）
        → Gate 2 命中后暂停，打印告警信息，等待用户输入 y/n。
        → 用户说 yes → 执行；no → deny。

三道都没命中 → 直接执行。大部分日常操作走这条路。
```

## 核心设计模式解读

1. **为什么把安全检查从工具实现里抽出来？**
   s01 的 `run_bash` 内部有一个 `dangerous` 列表，s02 没有动它。s03 把这个列表上移到了 `check_deny_list()`，变成了 Gate 1。好处是：安全检查不再和工具实现耦合。以后加 100 个工具，权限逻辑集中在管道里，不需要在每个工具里各写一遍 `if dangerous: return`。

2. **三道门的顺序为什么是固定的？**
   Gate 1（硬拒绝）最先跑，因为它在任何情况下都不需要用户参与——直接拦截最危险的操作，零延迟。Gate 2（规则匹配）次之，命中了才触发 Gate 3。如果 Gate 1 没拦、Gate 2 没命中，就直接放行，不打断用户。这个顺序用最小代价覆盖了从"绝对禁止"到"需要确认"的安全梯度。

3. **`check_permission()` 返回 bool 的意义**
   管道的接口只有一个：`bool`。True = 允许执行，False = 拦截。agent_loop 不关心内部是三道门还是三十道门——它只知道"问一下权限，通过了就执行"。这就是为什么只加了一行 `if not check_permission(block): continue`。循环的复杂度没有增长。

4. **s02 的 dispatch map + s03 的 permission pipeline 是正交的**
   加工具（s02）和加权限（s03）互不影响。`TOOL_HANDLERS` 管"能做什么"，`check_permission` 管"能不能做"。两个概念独立演进，循环代码保持稳定。
