> *"队友之间要有约定"* — request-response 协议 + request_id 关联 + 状态机。
>
> **Harness 层**: 协议 — Agent 之间的结构化握手。

```python
s16_team_protocols/code.py - 带 request-response 协议 + dispatch + 状态机的 Agent

s15 的队友能干活了，但协调是松散的：Lead 发消息，队友回复，没有结构化的约定。
两个场景暴露了问题：(1) 关机——直接杀线程会留下写了一半的文件；
(2) 计划审批——高风险操作应该先让 Lead 看计划再动手。

这两个场景结构完全一样：一方发请求，另一方给回复，请求和回复通过同一个 ID 关联。
有状态机追踪：pending → approved / rejected。不是"随便聊聊"，是"协议握手"。

s16 的回答：把约定的通信模式固化为协议。ProtocolState 追踪每个请求的状态，
handle_inbox_message 按消息类型分发，match_response 校验类型和状态，
consume_lead_inbox 统一消费解决 s15 的重复读竞态。

两种协议，一套机制：
  shutdown_request/response:  Lead → 队友，体面关机握手
  plan_approval_request/response: 队友 → Lead，计划审批示例

四步协议流程（以关机为例）：
  ① Lead 发请求:    new_request_id() → pending_requests[req_id] = ProtocolState(pending)
                    → BUS.send("shutdown_request", {request_id})
  ② 队友收到 dispatch: inbox → handle_inbox_message → 路由到 shutdown 分支
  ③ 队友回复:       BUS.send("shutdown_response", {request_id, approve: True})
  ④ Lead match:     match_response → 校验类型+状态 → pending_requests[req_id].status = approved

架构图：
    ┌─────────────────────────────────────────────────┐
    │  Lead (主线程)                                   │
    │                                                  │
    │  run_request_shutdown("alice")                   │
    │    → req_id = new_request_id()                   │
    │    → pending_requests[req_id] = ProtocolState()  │  ← 状态登记
    │    → BUS.send("shutdown_request",                │
    │         metadata={"request_id": req_id})          │
    └────────────────────┬────────────────────────────┘
                         │ .mailboxes/alice.jsonl
    ┌────────────────────▼────────────────────────────┐
    │  Teammate: "alice" (后台守护线程)                 │
    │                                                  │
    │  inbox = BUS.read_inbox("alice")                 │
    │  for msg in inbox:                               │
    │    msg_type = msg["type"]  # "shutdown_request"  │
    │    → handle_inbox_message(name, msg, messages)   │  ← 协议分发
    │      if shutdown_request:                        │
    │        BUS.send("shutdown_response",             │
    │          metadata={"request_id": req_id})         │
    │        return True  # 退出循环                    │
    └────────────────────┬────────────────────────────┘
                         │ .mailboxes/lead.jsonl
    ┌────────────────────▼────────────────────────────┐
    │  Lead: consume_lead_inbox()                      │
    │    for msg in inbox:                             │
    │      if msg_type.endswith("_response"):          │
    │        match_response(msg_type, req_id, approve) │  ← 协议匹配
    │          → 校验 request_id 存在                   │
    │          → 校验响应类型匹配请求类型                 │
    │          → 校验状态为 pending（防重复）            │
    │          → pending_requests[req_id].status = ✓    │
    │    return msgs  # 同时返回消息列表给 LLM           │
    └─────────────────────────────────────────────────┘

核心洞察："s15 的队友通信靠约定——Lead 发 'please stop'，队友可能不理。
        s16 把约定升级为协议——每条请求带 request_id，响应必须引用 request_id，
        Lead 端 match_response 做三层校验。不是'发条消息'，是'协议握手'。
        一种 FSM（pending→approved/rejected）支撑两种协议，
        新增协议类型只需加一个 msg_type 分支。"
```

### 💡 核心设计模式解读：

1. **s15 松散消息 vs s16 结构化协议：从聊天到握手**
   ```
   s15 (松散消息):   Lead → BUS.send("please stop") → alice 收到文本 → 可能不理
       无状态追踪，无类型区分，纯文本约定

   s16 (结构化协议): Lead → request_shutdown("alice") → ProtocolState(pending)
                     → BUS.send("shutdown_request", metadata={request_id})
                     → alice handle_inbox_message 分发
                     → BUS.send("shutdown_response", metadata={request_id})
                     → match_response 校验 → status = approved
       有状态机、有类型校验、有 request_id 关联、有重复消费防护
   ```
   s15 的"松散"不是 bug——它和你和同事在 Slack 上聊天一样。s16 的"结构化"是你和同事走审批流程：每一步有工单号、有状态。两种模式共存：日常沟通用 s15 的消息，正式决策用 s16 的协议。

2. **ProtocolState + pending_requests：一个 FSM 支撑所有协议**
   ```python
   @dataclass
   class ProtocolState:
       request_id: str      # "req_004281"
       type: str            # "shutdown" | "plan_approval"
       sender: str          # 发起方
       target: str          # 接收方
       status: str          # pending → approved | rejected
       payload: str         # 计划文本或关机原因
       created_at: float

   pending_requests: dict[str, ProtocolState] = {}  # 全局注册表
   ```
   为什么只用一个 `type` 字段区分而不建 `ShutdownRequest` 和 `PlanApprovalRequest` 两个子类？教学版的 `type` 字段是"标签型多态"——不需要完整的继承体系，两个协议的差异只在 handler 逻辑中，状态（pending→approved|rejected）是统一的。CC 的 15 种消息类型全部用这种方式：共用一个 message 结构，type 字段区分别不同处理。

3. **match_response 的三层校验：为什么不能省任何一个？**
   ```python
   def match_response(response_type, request_id, approve):
       state = pending_requests.get(request_id)
       if not state:                                    # 层1: request_id 存在？
           return
       if state.type == "shutdown" and response_type != "shutdown_response":
           return  # 层2: 类型匹配？（防误匹配）       # shutdown 不能用 plan 的响应
       if state.status != "pending":                    # 层3: 状态正确？（防重复处理）
           return
       state.status = "approved" if approve else "rejected"
   ```
   层 1 拦截无效 ID——可能是队友乱编的 `request_id`。层 2 拦截类型错配——一个 `shutdown_response` 不应该意外 approved 一个 `plan_approval` 请求。层 3 拦截重复处理——同一个 response 不能 approved 两次。三层校验按"从粗到细"的顺序：先看 ID 存不存在，再看类型对不对，最后看状态可不可变。如果顺序反过来——先检查状态——对于不存在的 request_id 会抛 KeyError。

4. **consume_lead_inbox: 统一消费解决 s15 的竞态**
   ```python
   # s15: check_inbox 工具和主循环各自读 inbox，存在竞态
   # run_check_inbox():    BUS.read_inbox("lead") → unlink
   # 主循环末尾:           BUS.read_inbox("lead") → 可能为空！（被工具消费了）

   # s16: 统一入口，两个调用者走同一个函数
   def consume_lead_inbox(route_protocol=True):
       msgs = BUS.read_inbox("lead")        # 只读一次
       if route_protocol:
           for msg in msgs:                 # 先路由协议消息
               if req_id and msg_type.endswith("_response"):
                   match_response(...)
       return msgs                          # 再返回消息列表（给 LLM 展示或注入 history）

   # run_check_inbox:  msgs = consume_lead_inbox(route_protocol=True)  → 返回字符串
   # 主循环末尾:       inbox_msgs = consume_lead_inbox(route_protocol=True)  → 注入 history
   ```
   不仅解决了"谁先读谁得"的竞态，还保证了"协议路由 + 消息展示"两步不会断裂——如果主循环没读到，协议状态不会更新；如果工具没读到，LLM 看不到队友的消息。统一入口保证了两件事一起做。

5. **handle_inbox_message: 按类型分发的 dispatch 模式**
   ```python
   def handle_inbox_message(name, msg, messages):
       msg_type = msg.get("type", "message")
       req_id = msg.get("metadata", {}).get("request_id", "")

       if msg_type == "shutdown_request":
           BUS.send(name, "lead", "Shutting down.", "shutdown_response",
                    {"request_id": req_id, "approve": True})
           return True   # 停止循环

       if msg_type == "plan_approval_response":
           approve = msg["metadata"].get("approve", False)
           messages.append({"role": "user",
               "content": "[Plan approved]" if approve else "[Plan rejected]"})
       return False      # 继续循环
   ```
   这和 s02 的 `TOOL_HANDLERS` dispatch map 是同一种模式——按 key（消息类型）分发到 handler。区别是这里用 if/elif 而非 dict，因为 handler 的签名不完全相同（shutdown 需要知道是否退出，plan 只需要注入消息）。dispatch 模式的核心价值是扩展性：新增协议类型只需加一个 if 分支，不影响已有逻辑。

6. **队友 idle loop: 从"10 轮退出"到"等 shutdown 才退"**
   ```python
   # s15: for _ in range(10) → 10 轮后强退
   # s16: while not shutdown_requested → 持续运行

   if response.stop_reason != "tool_use":
       # Idle 子循环：LLM 停下来后不退出，每秒轮询 inbox
       while not shutdown_requested:
           time.sleep(1)
           inbox = BUS.read_inbox(name)
           for msg in inbox:
               if msg.get("type") == "shutdown_request":
                   return True   # 收到关机指令才退出
               # 其他消息 → 注入 messages → break 回 LLM 轮次继续工作
   ```
   s15 的队友是一个"有倒计时的合同工"——最多干活 10 轮，到点走人。s16 的队友是"正式员工"——干完手头活就 idle，等新任务，直到收到正式"解聘通知"（shutdown_request）才体面退出。教学版省略了 idle_notification（CC 在 idle 时主动通知 Lead），但核心模式一致：持久等待 > 硬性限制。

7. **s15 → s16：加了 1 个数据类 + 4 个函数 + 3 个工具 + 1 个队友工具，循环更简洁**
   | 新增 | 说明 |
   |------|------|
   | `ProtocolState` dataclass | 7 字段：request_id/type/sender/target/status/payload/created_at |
   | `pending_requests` dict + `new_request_id` | 全局请求注册表 + ID 生成器 |
   | `match_response` | 响应匹配（三层校验：ID存在→类型匹配→状态检查） |
   | `consume_lead_inbox` | 统一收件箱消费（解决 s15 竞态） |
   | `handle_inbox_message` | 按消息类型分发到 handler |
   | `_teammate_submit_plan` | 队友提交计划（协议级请求） |
   | `run_request_shutdown` / `run_request_plan` / `run_review_plan` | 3 个新 Lead 协议工具 |
   | 队友新增 `submit_plan` 工具 | 队友可按协议提交计划等待审批 |
   | 队友 idle loop | 从 10 轮硬限制升级为 `while not shutdown_requested` |
   | MessageBus 新增 `metadata` 参数 | 消息携协议关联信息 |

   移除：s16 教学版移除了 cron 调度器（聚焦团队协议），agent_loop 更简洁——没有 `consume_cron_queue()` 调用。工具总数 14（换 3 个协议工具换下了 3 个 cron 工具）。
