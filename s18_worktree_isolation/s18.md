> *"各干各的目录, 互不干扰"* — 任务管目标, worktree 管目录, 按 ID 绑定。
>
> **Harness 层**: 隔离 — 并行执行的目录隔离。

```python
s18_worktree_isolation/code.py - 带 git worktree + 任务绑定 + 安全收尾的 Agent

s17 中，Alice 和 Bob 都在同一个目录下工作。Alice 的任务是"重构认证模块"，
Bob 的任务是"重构 UI 登录页"。Alice write_file("config.py", ...)，
Bob 也 write_file("config.py", ...)——两个人改同一个文件，互相覆盖。
而且无法干净地回滚——分不清哪些改动是谁的。

s18 的回答：给每个任务一个独立的 git worktree。Alice 在 .worktrees/auth/ 下干活，
Bob 在 .worktrees/ui/ 下干活，互不干扰。任务完成后 Lead 审查 worktree 变更，
决定 keep（保留分支等 review）还是 remove（清理）。事件日志记录每次生命周期操作，
可审计。

s17 共享目录 vs s18 worktree 隔离:
  s17 (共享):  all agents share WORKDIR → alice writes config.py, bob overwrites it
  s18 (隔离):  task → create_worktree → bind → agent works in .worktrees/{name}/
               ↑ 每个任务的改动在自己的分支 wt/{name} 上

三个工具，三种收尾:
  create_worktree:  创建独立 git worktree + 可选绑定任务（不改任务状态）
  remove_worktree:  安全检查（有未提交改动默认拒绝）→ git worktree remove --force
  keep_worktree:    保留 worktree 和分支，供人工审查后合并

架构图：
    ┌─────────────────────────────────────────────────┐
    │  Lead (主线程)                                   │

    │  spawn_teammate("bob", ...)                       │
    └─────────────┬───────────────────────────────────┘
                  │
    ┌─────────────▼───────────────────────────────────┐
    │  文件系统拓扑                                     │
    │  Main repo /                                     │
    │    ├── .worktrees/auth/  (branch: wt/auth)       │
    │    │     └── config.py   ← Alice 改这里           │
    │    ├── .worktrees/ui/    (branch: wt/ui)          │
    │    │     └── config.py   ← Bob 改这里（互不干扰） │

    │    → _run_bash: cwd=.worktrees/auth/             │
    │    → _run_write: cwd=.worktrees/auth/            │
    │  WORK → write_file("config.py", ...)             │
    │    → 文件写入 .worktrees/auth/config.py           │
    │  complete_task → wt_ctx["path"] = None           │
    │  IDLE → ... → SHUTDOWN                           │
    └─────────────────────────────────────────────────┘

    └─────────────────────────────────────────────────┘

核心洞察："s17 的队友自组织了，但都在一个目录下干活——Alice 改 config.py，
        Bob 也改 config.py，互相覆盖。s18 不是让队友'注意别覆盖'，
        而是给每个任务一个 git worktree——物理隔离，从根源上解决冲突。
        任务-Worktree 绑定只写 worktree 字段不改变状态（pending→pending），
        队友认领后才通过 wt_ctx 自动切换工作目录。完成任务后再决定清理还是保留。"
```

### 💡 核心设计模式解读：

1. **s17 共享目录 vs s18 worktree 隔离：从约定到物理隔离**
   ```
   s17 (共享目录): Alice 和 Bob 都在 WORKDIR 下工作
       write_file("config.py") → 同一个文件 → 互相覆盖
       解决方案? 沟通约定"你改 auth/config.py，我改 ui/login.py" → 靠自觉

   s18 (物理隔离): Alice 的 bash 在 .worktrees/auth/ 执行
       Bob 的 bash 在 .worktrees/ui/ 执行
       write_file("config.py") → auth/config.py vs ui/config.py → 不冲突
       解决方案: git worktree 物理隔离 → 不需要自觉
   ```
   s17 的共享目录问题是"并发修改同一资源"。解决它不应该靠"队友自觉"——那是人处理冲突的方式。解决靠的是物理隔离——每个任务有自己的工作目录和分支，文件系统层面就不可能冲突。

2. **bind_task_to_worktree: 为什么只写 worktree 字段不改状态？**
   ```python
   def bind_task_to_worktree(task_id: str, worktree_name: str):
       task = load_task(task_id)
       task.worktree = worktree_name     # 只写 worktree 字段
       save_task(task)                   # 状态保持 pending，不改 owner/status
   ```
   bind 不改 `status` 也不设 `owner`——任务仍是 `pending`，等队友自动认领。如果 bind 同时把任务设为 `in_progress`，那就破坏了 s17 的自治认领流程。Lead 创建任务 + 创建 worktree + 绑定，队友在 IDLE 阶段 `scan_unclaimed_tasks()` 时发现 `pending + worktree="auth"`，自动认领。绑定和认领是两个独立步骤：绑定="这个任务在哪个目录做"，认领="我来做这个任务"。

3. **wt_ctx 闭包模式：队友的 worktree 感知 cwd**
   ```python
   wt_ctx = {"path": None}  # 用 dict 而非裸变量——闭包可以修改 dict 内部值

   def _run_claim_task(task_id):
       result = claim_task(task_id, owner=name)
       if "Claimed" in result:
           task = load_task(task_id)
           if task.worktree:
               wt_ctx["path"] = str(WORKTREES_DIR / task.worktree)  # 设置 cwd
           else:
               wt_ctx["path"] = None
       return result

   def _run_bash(command):
       return run_bash(command, cwd=_wt_cwd())  # 自动在 worktree 下执行

   def _run_complete_task(task_id):
       result = complete_task(task_id)
       wt_ctx["path"] = None  # 清除 cwd——下一个任务可能有不同 worktree
       return result
   ```
   为什么用 `wt_ctx = {"path": None}` 而不是裸变量 `wt_path = None`？Python 闭包中修改外部变量需要用 `nonlocal` 声明，而修改 dict 内部值不需要——`wt_ctx["path"] = x` 可以在任何深度的闭包中工作。这是一个常见的 Python 模式。`_run_complete_task` 清除了 wt_ctx——因为下一个认领的任务可能有不同的 worktree（或没有 worktree），残留的旧路径会导致文件写错位置。

4. **remove_worktree 的安全检查：_count_worktree_changes 的统计逻辑**
   ```python
   def _count_worktree_changes(path):
       r1 = subprocess.run(["git", "status", "--porcelain"], cwd=path)
       files = len(...)    # 未提交的文件数
       r2 = subprocess.run(["git", "log", "@{push}..HEAD", "--oneline"], cwd=path)
       commits = len(...)  # 未推送的提交数
       return files, commits

   def remove_worktree(name, discard_changes=False):
       if not discard_changes:
           files, commits = _count_worktree_changes(path)
           if files > 0 or commits > 0:
               return "有未提交改动...使用 discard_changes=true 强制删除"
       run_git(["worktree", "remove", str(path), "--force"])
       run_git(["branch", "-D", f"wt/{name}"])  # 删除分支
   ```
   安全检查在删除前帮你确认"这个 worktree 里是不是有还没处理完的工作"。`--porcelain` 是 git status 的机器可读模式，稳定不随语言变化。`@{push}..HEAD` 检查未推送的提交——如果有本地提交但没推送，删除 worktree 会丢工作。CLI 的 `discard_changes=true` 是手动确认"我知道有改动，但我就是要删"。

5. **validate_worktree_name: 正则白名单防止路径穿越**
   ```python
   VALID_WT_NAME = re.compile(r'^[A-Za-z0-9._-]{1,64}$')

   def validate_worktree_name(name):
       if not name: return "不能为空"
       if name == "." or name == "..": return "非法"
       if not VALID_WT_NAME.match(name): return "只允许字母数字 ._-"
       return None
   ```
   如果允许任意 name，`create_worktree("../etc", ...)` 会把 worktree 创建到 `.worktrees/../etc` = 仓库外的 `/etc` 目录。正则白名单 `^[...]{1,64}$` 用 `^` 和 `$` 锚定整串——不接受含有 `/` 或任何非常见字符的名称。白名单比黑名单安全：你不知道攻击者会用什么路径穿越技巧（`...`、`..%2f`、Unicode 等价），但你知道什么字符是安全的。

6. **log_event: 事件日志为什么是 append-only？**
   ```python
   def log_event(event_type, worktree_name, task_id=""):
       event = {"type": event_type, "worktree": worktree_name,
                "task_id": task_id, "ts": time.time()}
       with open(events_file, "a") as f:  # append-only
           f.write(json.dumps(event) + "\n")
   ```
   events.jsonl 是 append-only——不修改、不删除已有记录。这保证了两点：(1) 并发安全——多个 worktree 操作可以同时 append，不需要文件锁；(2) 审计追溯——你可以 `cat events.jsonl` 看每个 worktree 的完整生命周期：`create→keep` 或 `create→remove`。`run_git` 在创建/删除成功后才写事件日志——日志只记录真实发生的操作，不记录失败的尝试。

7. **s17 → s18：加了 5 个函数 + 1 个数据字段 + 3 个工具 + cwd 参数，循环不变**
   | 新增 | 说明 |
   |------|------|
   | `Task.worktree` 字段 | 任务可绑定独立工作目录名称 |
   | `validate_worktree_name` | 正则白名单防路径穿越 |
   | `run_git` | 统一 git 执行入口（返回 ok/output 元组） |
   | `log_event` | append-only 事件日志（events.jsonl） |
   | `create_worktree` | git worktree add + 可选 bind + 事件记录 |
   | `bind_task_to_worktree` | 只写 worktree 字段，不改 status/owner |
   | `_count_worktree_changes` | 统计未提交文件和未推送提交 |
   | `remove_worktree` | 安全检查 + git worktree remove + 删除分支 |
   | `keep_worktree` | 保留分支供审查 |
   | `safe_path` / `run_bash` / `run_read` / `run_write` 新增 `cwd` 参数 | 支持 worktree 目录作为工作目录 |
   | 队友 `wt_ctx` 闭包 | claim 时设置 cwd，complete 时清除 |
   | `idle_poll` worktree 感知 | auto-claim 时注入 worktree 路径信息 |
   | 3 个 Lead 工具 | create_worktree / remove_worktree / keep_worktree |

   循环里的改动：agent_loop 完全不变。所有 worktree 逻辑都在 (1) Lead 的工具调用层 和 (2) 队友线程的 wt_ctx 闭包中。基本工具（bash/read/write）新增了 `cwd` 可选参数——这是 s18 对"基础设施"的唯一改动，队友通过闭包传 worktree 路径，Lead 端不传则使用默认目录。
