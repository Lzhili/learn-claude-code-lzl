> *"慢操作丢后台, agent 继续干活"* — 守护线程异步执行 + 通知注入。
>
> **Harness 层**: 后台 — 异步执行, 不阻塞主循环。

```python
s13_background_tasks/code.py - 带后台线程 + <task_notification> 通知注入的 Agent

s12 的 Agent 处理慢操作时纯同步——pip install torch 跑 10 分钟，agent 就干等 10 分钟。
bash 工具的 timeout 是 120 秒，但有些命令（install/build/test）几分钟甚至更长，
agent 循环被阻塞在 subprocess.run 上，什么也做不了。

s13 的回答：把慢操作扔给 daemon 线程后台跑，agent 主循环先收到占位符继续干活，
后台完成后通过 <task_notification> 格式注入结果。

两条判断路径决定哪些操作放后台:
  路径 A (显式): 模型通过 bash 的 run_in_background=True 参数主动声明
  路径 B (启发式): 关键词匹配——install/build/test/deploy/compile 等

架构图：

核心洞察："s12 之前，agent_loop 假设所有工具调用都可以同步等结果。s13 把这个假设改成了
         '快操作同步等，慢操作后台跑，结果回头通知'。区分快慢 + 分离轨道，
         让 agent 从'干等'变成'并行'。"
```

### 💡 核心设计模式解读：

1. **同步 vs 后台：两种时间线的对比**
   ```python
   # s12: 同步模式——agent 被 npm install 阻塞 3 分钟
   output = run_bash("npm install && npm run build")
   # agent 什么也做不了，LLM 空转

   # s13: 后台模式——agent 收到占位符，继续工作
   if should_run_background("bash", {"command": "npm install && npm run build"}):
       bg_id = start_background_task(block)      # 后台线程跑
       results.append({"tool_use_id": block.id,
           "content": f"[Background task {bg_id} started]..."})  # 占位符
   # agent 立即可以处理下一轮——读文件、创建任务、回复用户
   ```
   这不是"异步语法糖"，而是**时间线分离**。前台时间线（LLM 对话->工具调用->LLM 对话）保持毫秒/秒级响应，后台时间线（npm install->3min->完成通知）独立运行，两条线只在 `collect_background_results()` 处交汇。

2. **should_run_background: 两层判断，谁优先？**
   ```python
   def should_run_background(tool_name: str, tool_input: dict) -> bool:
       """Model explicit request takes priority; fallback to heuristic."""
       if tool_input.get("run_in_background"):    # 层1: 模型显式声明
           return True
       return is_slow_operation(tool_name, tool_input)  # 层2: 关键词启发式
   ```
   模型显式请求优先。LLM 比关键词启发式更聪明——它知道 `npm install` 在全新项目里需要 10 分钟，在已有 node_modules 的项目里可能只需要 2 秒。启发式是兜底，不是主路径。CC 的 bash 工具 schema 里有 `run_in_background: boolean` 参数（`BashTool.tsx:241`），模型自己决定哪些命令丢后台。

3. **三个共享字典 + 一把锁：简化版的线程安全**
   ```python
   _bg_counter = 0                    # 全局递增计数器
   background_tasks: dict = {}        # bg_id → {tool_use_id, command, status}
   background_results: dict = {}      # bg_id → output
   background_lock = threading.Lock() # 互斥锁

   def worker():
       result = execute_tool(block)
       with background_lock:          # 加锁写入
           background_tasks[bg_id]["status"] = "completed"
           background_results[bg_id] = result
   ```
   为什么要分两个字典？`background_tasks` 存生命周期（running/completed），`background_results` 存输出。两者生命周期不同——collect 时先检查 `background_tasks` 中的 status 判断完成，再 pop 出 `background_results` 中的内容。如果合并成一个字典，pop + 检查 status 就是一次操作，但教学代码保持了清晰的语义分离。`daemon=True` 确保主线程退出时自动回收。

4. **collect_background_results: pop 取走，不复用 tool_use_id**
   ```python
   def collect_background_results() -> list[str]:
       with background_lock:
           ready_ids = [bid for bid, task in background_tasks.items()
                        if task["status"] == "completed"]
       notifications = []
       for bg_id in ready_ids:
           with background_lock:
               task = background_tasks.pop(bg_id)      # 取出即清理
               output = background_results.pop(bg_id, "")  # 避免重复注入
           notifications.append(
               f"<task_notification>\n"
               f"  <task_id>{bg_id}</task_id>\n"       # 新的 bg_id，不是 tool_use_id
               f"  <status>completed</status>\n"
               f"  <command>{task['command']}</command>\n"
               f"  <summary>{output[:200]}</summary>\n"
               f"</task_notification>")
       return notifications
   ```
   `pop` 不是 `get`——取出后就从字典里删了，不会下次再收集到同一个通知。通知格式是独立的结构化 XML `<task_notification>`，不复用原始 `tool_use_id`。这是 API 协议约束：一个 `tool_use_id` 只能对应一个 `tool_result`。后台完成是独立事件，对原始 tool call 已经用过 `tool_result` 回了占位符。

5. **agent_loop 的分流：if/else 决定前台/后台**
   ```python
   results = []
   for block in response.content:
       if block.type != "tool_use":
           continue
       if should_run_background(block.name, block.input):
           bg_id = start_background_task(block)        # 后台路径
           results.append({"tool_use_id": block.id,
               "content": f"[Background task {bg_id} started]..."})  # 占位符
       else:
           output = execute_tool(block)                 # 前台路径
           results.append({"tool_use_id": block.id,
               "content": output})                      # 立即结果
   ```
   两条路径的唯一差异是 tool_result 的 content：后台路径返回"已启动"占位符，前台路径返回真实输出。`tool_use_id` 配对不变——API 规范要求每个 tool_use 必须有一个 tool_result，即使是占位符。

6. **通知与工具结果的合并：一条 user 消息容纳两个来源**
   ```python
   user_content = list(results)                         # 先放工具结果
   bg_notifications = collect_background_results()      # 收集后台通知
   if bg_notifications:
       for notif in bg_notifications:
           user_content.append({"type": "text", "text": notif})  # 再追加通知
   messages.append({"role": "user", "content": user_content})
   ```
   后台通知是 `text` 类型，不是 `tool_result` 类型——因为它们没有对应的 tool_use。它们作为独立的 text block 追加到同一条 user 消息中。LLM 在下一轮看到这条 user 消息时，同时看到"这轮工具的结果"和"之前后台任务的完成通知"，在一个 turn 内消化两组信息。

7. **s12 → s13：加了 4 个函数 + 3 个共享变量 + 1 个锁，循环多了 1 个 if/else**
   | 新增 | 说明 |
   |------|------|
   | `_bg_counter` + `background_tasks` + `background_results` + `background_lock` | 后台任务生命周期管理 |
   | `is_slow_operation` | 启发式慢操作判断（关键词匹配） |
   | `should_run_background` | 两层判断：显式声明 → 启发式回退 |
   | `execute_tool` | 工具统一执行入口（handler dispatch） |
   | `start_background_task` | 分发到守护线程 + 返回 bg_id |
   | `collect_background_results` | 收集完成通知 + XML 格式化 |
   | bash 工具 schema 新增 `run_in_background: boolean` | 模型可主动声明后台执行 |

   循环里的改动：工具执行从 `output = handler(**block.input)` 变成 `if should_run_background → start_background_task / else → execute_tool`，外加通知收集。s12 的 8 个工具不变，执行策略变了——工具数没变，调用方式改了。
