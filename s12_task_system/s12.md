### 💡 核心设计模式解读：

1. **s05 TodoWrite vs s12 Task System：从列表到图**
   ```
   s05: todos = [{content:"搭数据库", status:"pending"}, {content:"写API", status:"pending"}]
        → 平铺列表，无依赖，退出就没了

   s12: task_schema = {id:"..", subject:"设计表结构", blockedBy:[]}
        task_api    = {id:"..", subject:"写API",       blockedBy:["task_schema"]}
        task_test   = {id:"..", subject:"加测试",      blockedBy:["task_api"]}
        → 有向图，JSON 持久化，跨会话保留
   ```
   TodoWrite 管的是"我现在做什么"，Task System 管的是"整个项目应该按什么顺序做"。两者不冲突——s05 适合单任务步骤规划，s12 适合多任务依赖编排。

2. **为什么用文件系统而不是数据库？**
   ```python
   TASKS_DIR = WORKDIR / ".tasks"
   def _task_path(task_id): return TASKS_DIR / f"{task_id}.json"
   def save_task(task): _task_path(task.id).write_text(json.dumps(asdict(task), indent=2))
   def list_tasks(): return [Task(**json.loads(p.read_text())) for p in sorted(TASKS_DIR.glob("task_*.json"))]
   ```
   三个理由：(1) 零依赖——不需要 SQLite/Redis；(2) 人类可读——`cat .tasks/task_*.json` 直接看；(3) Agent 可操作——LLM 用 `read_file`/`write_file` 就能查看修改。CC 源码做同样选择：任务存在 `~/.claude/tasks/{taskListId}/{taskId}.json`。

3. **can_start: 依赖检查的两层判断**
   ```python
   def can_start(task_id: str) -> bool:
       task = load_task(task_id)
       for dep_id in task.blockedBy:
           if not _task_path(dep_id).exists():    # 层1: 依赖文件存在？
               return False
           if load_task(dep_id).status != "completed":  # 层2: 依赖已完成？
               return False
       return True
   ```
   两层判断的顺序不能换。先检查文件存在——如果依赖任务根本不存在，连看它状态的资格都没有。再检查状态——即使文件存在，没完成就是阻塞。这两层对应两种不同的阻塞场景："依赖不存在"（可能是 ID 写错了）和"依赖未完成"（正常等待）。

4. **complete_task 的传播：完成不是终点**
   ```python
   def complete_task(task_id: str) -> str:
       task.status = "completed"
       save_task(task)
       unblocked = [t.subject for t in list_tasks()
                    if t.status == "pending" and t.blockedBy and can_start(t.id)]
       if unblocked:
           msg += f"\nUnblocked: {', '.join(unblocked)}"
   ```
   这是一个"写传播"——完成一个任务后，不声明"谁来接着干"，而是遍历所有 pending 任务，逐个检查 can_start。如果某个待办任务的依赖因这次完成而全部满足，它的 subject 就被追加到返回值中。LLM 看到这条返回内容就知道"接下来可以认领这些了"。CC 源码有 `TaskCompleted` hook 事件做同样的事，供外部系统（通知、上游依赖触发）订阅。

5. **claim_task: 领取任务的三道验证**
   ```python
   def claim_task(task_id, owner="agent"):
       if task.status != "pending":         # 验证1: 状态正确
           return f"Task {task_id} is {task.status}, cannot claim"
       if not can_start(task_id):           # 验证2: 依赖满足
           return f"Blocked by: {deps}"
       task.owner = owner                   # 通过验证 → 认领
       task.status = "in_progress"
   ```
   依次验证状态（pending）→ 依赖（can_start）→ 没有任何一个检查是多余的。状态不对意味着已经被别人领了或已完成；依赖不满足意味着前置工作没做完。两个都通过后才 `owner = agent`，然后 `status = "in_progress"`。owner 字段为多 Agent 协作预留——如果将来有多个 Agent 同时工作，看到 `owner: "agent-2"` 就知道这个任务已经有人在做了。

6. **五个工具不是随意分的——每个映射到任务生命周期的一个节点**
   ```
   create_task  →  诞生（pending）
   claim_task   →  激活（pending → in_progress）
   complete_task → 完成（in_progress → completed）
   list_tasks   →  全览（任何时候）
   get_task     →  深查（需要详细信息时）
   ```
   如果只有一个通用 `update_task` 工具，LLM 需要自己理解"pending→in_progress=认领" vs "in_progress→completed=完成"的区别，容易出错。五个专用工具让每个操作都有明确的入参和语义——create 需要 subject，claim 需要 task_id，complete 也需要 task_id——LLM 不需要推导隐式状态机。

7. **s11 → s12：加了 1 个数据类 + 9 个函数 + 5 个工具定义，循环基本不动**
   | 新增 | 说明 |
   |------|------|
   | `Task` dataclass | 6 字段：id/subject/description/status/owner/blockedBy |
   | `_task_path` | 任务文件路径助手 |
   | `create_task` / `save_task` / `load_task` | CRUD 基础 |
   | `list_tasks` / `get_task` | 查询 |
   | `can_start` | 依赖检查（两层判断） |
   | `claim_task` | 认领（三道验证） |
   | `complete_task` | 完成 + 传播解封 |
   | 5 个工具 schema + 5 个 `run_*` handler | TOOLS + TOOL_HANDLERS 注册 |
   
   循环里的改动：TOOLS 数组从 3 个增加到 8 个。除此之外循环代码不变——task 工具完全通过 dispatch map 分发，不需要循环知道它们的存在。s02 的 dispatch map 模式在第 8 次扩展时依然有效。
