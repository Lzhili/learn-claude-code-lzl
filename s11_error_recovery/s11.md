> *"错误不是终点, 是重试的起点"* — 升级 token、压缩上下文、切换模型。
>
> **Harness 层**: 韧性 — 主循环遇到错误时分类并恢复。

```python
s11_error_recovery/code.py - 带三条恢复路径 + 指数退避的 Agent

s01-s10 的 Agent 跑着跑着报错了:

    Error: 529 overloaded

Agent 崩溃了。它没有重试，没有换模型，没有减少上下文——直接崩溃。

s11 的回答：把 LLM 调用包装在 try/except 里，根据错误类型走不同的恢复路径。
恢复后 continue 回到循环开头重新调用 LLM。

三条恢复路径，对应三种最常见的故障:
  Path 1 (max_tokens): 输出截断 → 升级 8K→64K（0 API 调用）→ 续写提示（动态调整）
  Path 2 (prompt_too_long): 上下文超限 → 紧急压缩 → 重试（1 次机会）
  Path 3 (429/529): 瞬时故障 → 指数退避 + 抖动（最多 10 次）→ 连续 529 切换模型

架构图：
    ┌──────────────────────────────────────────────────┐
    │            agent_loop(messages, context)          │
    │  system = get_system_prompt(context)              │  ← s10 prompt 组装
    │  state = RecoveryState()                          │  ← 追踪所有恢复动作
    │  max_tokens = 8000                                │
    └────────────────────┬─────────────────────────────┘
                         │
    ┌────────────────────▼─────────────────────────────┐
    │  try:                                             │
    │    response = with_retry(fn, state)  ← LLM 调用   │
    │         │                                          │
    │         ├─ 成功 → 返回 response                    │
    │         ├─ 429 → 退避 + 重试（最多 10 次）         │
    │         └─ 529 → 退避 + 重试 + 连续 3 次换模型     │
    │                                                    │
    │  except PromptTooLong:                             │
    │    messages[:] = reactive_compact(messages)  ← 1 次│
    │                                                    │
    │  except Other:                                     │
    │    日志 + 退出                                     │
    └────────────────────┬─────────────────────────────┘
                         │
    ┌────────────────────▼─────────────────────────────┐
    │  if stop_reason == "max_tokens":                  │
    │    首次 → max_tokens = 64000, continue            │  ← 不追加截断输出
    │    再次 → 保存截断输出 + 续写提示（最多 3 次）       │
    │    超过 → 退出                                     │
    │                                                    │
    │  else:                                             │
    │    messages.append(response)                       │  ← 正常追加
    │    if stop_reason != "tool_use": return            │
    └────────────────────┬─────────────────────────────┘
                         │
                         ▼
                    工具执行 → 循环

核心洞察："s10 之前，agent_loop 假设 LLM 调用'总是成功'。s11 把这个假设改成了
         'LLM 调用可能失败，但大部分失败可恢复'。错误分类 + 分级处理，
         让 Agent 从'一碰就熄火'变成'倒了能爬起来'。"
```

### 💡 核心设计模式解读：

1. **三条路径为什么不能合并？为什么 max_tokens 不放在 except 块里？**
   `max_tokens` 不是异常——API 调用成功了，模型返回了完整的 HTTP 200，只是输出被截断了。它通过 `response.stop_reason` 暴露，而不是通过 `raise Exception`。如果把 max_tokens 放在 except 里，就永远捕获不到它。三种恢复路径的分流逻辑：
   ```
   with_retry(LLM_call)              ← Path 3: 在内部处理 429/529
       ↓ 成功拿到 response
   if stop_reason == "max_tokens":   ← Path 1: response 层面的截断
       escalate / continue
   except prompt_too_long:           ← Path 2: API 返回的错误
       reactive compact / continue
   except other:                     ← 兜底: 真的不可恢复
       log + exit
   ```

2. **Path 1 的两次升级为什么不追加截断输出？**
   ```python
   if response.stop_reason == "max_tokens":
       if not state.has_escalated:
           max_tokens = ESCALATED_MAX_TOKENS    # 8K → 64K
           state.has_escalated = True
           continue                             # ← 不追加 response，重试同一请求
       # 64K 还是截断 → 追加截断输出 + 续写提示
       messages.append({"role": "assistant", "content": response.content})
       messages.append({"role": "user", "content": CONTINUATION_PROMPT})
   ```
   第一次升级时不追加截断输出，而是 `continue` 重发同一请求。因为 8K 截断的输出可能停在句子中间，把不完整的输出追加给 LLM 会让它困惑。升级到 64K 后，同样的 prompt 同样的上下文，模型有机会输出完整回答。64K 还是不够时，才接受"这次真写不下了"，追加截断内容并给续写提示。

3. **Path 2 的 reactive_compact 为什么只有 1 次机会？**
   ```python
   except Exception as e:
       if is_prompt_too_long_error(e):
           if not state.has_attempted_reactive_compact:
               messages[:] = reactive_compact(messages)  # 保留最后 5 条
               state.has_attempted_reactive_compact = True
               continue
           # 压缩过了还是超 → 退出
   ```
   教学版的 `reactive_compact` 只做尾部保留（最后 5 条消息）。如果 5 条消息 + system prompt 还是超——那说明这 5 条中有一条是巨大且没法再压缩的。重复压缩只会得到同样的消息列表。1 次是上限，不是因为"再试可能成功"，而是因为"再试一定不会不一样"。

4. **Path 3: 指数退避 + 随机抖动 = 避免惊群效应**
   ```python
   def retry_delay(attempt, retry_after=None):
       base = min(BASE_DELAY_MS * (2 ** attempt), 32000) / 1000  # 500ms, 1s, 2s, 4s...
       jitter = random.uniform(0, base * 0.25)                    # 0~25% 随机
       return base + jitter
   ```
   退避表：第 1 次 0.5s，第 2 次 1s，第 3 次 2s...上限 32s。加 ±25% 随机抖动让多个并发客户端不会在同一毫秒同时重试——这就是"惊群效应"（thundering herd）的缓解。如果服务器返回 `Retry-After` header，教学版优先用那个值。

5. **529 过载 → 切换备选模型的链式判断**
   ```python
   state.consecutive_529 += 1
   if state.consecutive_529 >= 3:        # 连续 3 次都 529
       if FALLBACK_MODEL:                # 配置了备选模型？
           state.current_model = FALLBACK_MODEL  # 切过去
           state.consecutive_529 = 0            # 重置计数器
       else:
           state.consecutive_529 = 0     # 没配置就继续当前模型重试
   ```
   不是一次 529 就切模型——连续 3 次才切。一次可能是瞬时负载波动，3 次说明这台实例真的饱和了。切换到备选模型后计数器重置——如果备选模型也 529，再累积 3 次后...没有第二个备选模型，只能继续退避重试。

6. **RecoveryState: 五个字段，五种记忆**
   ```python
   class RecoveryState:
       has_escalated: bool              # 是否已经升级过 max_tokens
       recovery_count: int              # 续写提示已发次数
       consecutive_529: int             # 连续过载计数
       has_attempted_reactive_compact: bool  # 是否尝试过紧急压缩
       current_model: str               # 当前使用的模型 ID
   ```
   这五个字段不是随意分的。每个字段对应一个"只能做一次"或"有上限"的决策：`has_escalated` 防止无限升级，`has_attempted_reactive_compact` 防止重复压缩，`recovery_count` 限制续写次数，`consecutive_529` 控制模型切换。状态类的价值不是"存数据"，而是"记住自己做过的恢复动作，防止同一个动作反复做"。

7. **s10 → s11：加了 4 个函数 + 1 个类，循环只多了 1 层 try/except**
   | 新增 | 说明 |
   |------|------|
   | `RecoveryState` | 恢复状态类（5 字段） |
   | `retry_delay(attempt)` | 指数退避 + 抖动 |
   | `with_retry(fn, state)` | Path 3 包装器（处理 429/529） |
   | `is_prompt_too_long_error(e)` | 判断是否上下文超限 |
   | `reactive_compact(messages)` | Path 2 紧急压缩（保留尾 5 条） |
   
   循环里的改动：`client.messages.create(...)` 变成了 `with_retry(lambda: client.messages.create(...), state)`。外加 1 个 if/elif 用于 Path 1 的 max_tokens 处理。s10 的 prompt 组装、工具执行、context 刷新全部不变。错误恢复完全在 LLM 调用层做，不侵入工具层。
