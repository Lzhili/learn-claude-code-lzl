> *"机制很多，循环一个"* — 工具、权限、记忆、任务、团队、插件都挂在同一个 while True 上。
>
> **Harness 层**: 综合 — 把前 19 章的机制放回同一个可运行系统。

```python
s20_comprehensive/code.py - 全部教学组件合一，一个循环挂所有机制的完整 Agent

s01 到 s19 每章只加一个机制。这样适合学习，但真实 Agent 不会只带一个机制运行。
一个能长期工作的 coding agent 需要同时拥有：工具分发、权限边界、hooks 扩展点、
todo 计划和任务图、技能加载、记忆系统、上下文压缩、错误恢复、后台任务、
cron 调度、团队协作、协议握手、自治认领、worktree 隔离、MCP 外部工具接入。

s20 的回答：不是再加一个新机制，而是把前面 19 个机制放回同一个循环上。
每个机制在循环中的位置是明确的——该在 LLM 前跑的，该在 LLM 后跑的，
该在工具执行前后挂钩子上的，各就各位。

核心不变：
  while True:
      response = LLM(messages, tools)
      if not has_tool_use(response.content):
          return
      results = execute_tools(response.content)
      messages.append(tool_results)

变了的是循环周围的 harness——s20 的 while True 每轮经过 14 道工序。

组件在循环中的位置：
  ┌─ 用户输入前后: UserPromptSubmit hooks（记录、注入、审计）
  │
  ├─ LLM 前 (1): cron queue（定时触发 → [Scheduled] ... 注入 messages）
  ├─ LLM 前 (2): background notifications（后台完成 → <task_notification> 注入）
  ├─ LLM 前 (3): todo reminder（3 轮未更新 → <reminder> 注入）
  ├─ LLM 前 (4): compaction pipeline（L1 snip → L2 micro → L3 budget → L4 auto compact）
  ├─ LLM 前 (5): memory + skills + MCP 状态（组装 system prompt）
  │
  ├─ LLM 调用: error recovery（429/529 重试 + max_tokens 升级 + prompt_too_long compact）
  │
  ├─ 工具执行前: PreToolUse hooks + permission（拒绝危险命令、越界写、破坏性 MCP）
  ├─ 工具分发: assemble_tool_pool（内置 27 工具 + MCP 动态工具）
  ├─ 工具执行时: background dispatch（慢操作丢 daemon thread，主循环先返占位符）
  ├─ 工具执行后: PostToolUse hooks（大输出告警、日志后处理）
  │
  ├─ 返回循环: tool_result（每个 tool_use 对应一个 tool_result → 下一轮）
  └─ 本轮停止: Stop hooks（统计、审计、清理）
```

### 💡 核心设计模式解读：

1. **从教学到实战：拆开和合回的两种视角**
   ```
   s01-s19 (教学视角): 每次只加一个机制
       s01: while True + LLM → tool_use? → execute → loop
       s02: + dispatch map (TOOL_HANDLERS)
       s03: + permission pipeline
       ...每个都从上一个代码 copy 一份，只加新东西
       → 你能看清楚每个机制的独立逻辑

   s20 (实战视角): 所有机制合一
       while True:
           ① cron注入 ② bg通知 ③ todo提醒
           ④ 压缩管道 ⑤ prompt组装 ⑥ LLM+恢复
           ⑦ hooks+permission+tools+bg dispatch
           ⑧ 结果组装 → loop
       → 你能看清楚每个机制在循环中的位置
   ```
   两种视角不冲突——拆开是为了学习每个机制，合回是为了理解整体架构。s20 的价值不是"功能更多了"，而是"每个功能挂在循环的哪个位置"变得一目了然。

2. **14 道工序的顺序：为什么不能随意调换？**
   ```
   ① cron注入        → 在 LLM 之前，让定时任务进入本轮上下文
   ② bg通知注入      → 在 LLM 之前，让已完成的后台结果可见
   ③ todo提醒        → 在 LLM 之前，让模型不忘记更新计划
   ④ 压缩管道        → 在 LLM 之前，控制上下文大小避免超限
   ⑤ prompt组装      → 在 LLM 之前，注入最新的记忆/MCP/skills 信息
   ⑥ LLM调用+恢复    → 核心步骤
   ⑦ hooks+permission → 在工具执行前，拦截检查
   ⑧ 工具分发        → 实际执行
   ⑨ 结果组装        → 在 LLM 之后，把结果送回消息历史
   ```
   如果把 ④ 放在 ① 之前——compaction 跑完后再注入 cron/bg/todo 消息，注入后就没机会做压缩预算检查了——如果压缩后上下文刚好接近极限，新注入的消息可能让本轮超限。当前顺序（先注入 → 再统一压缩）让 LLM 看到的是一个"完整且不超限"的上下文。如果把 ⑤ 放在 ⑥ 之后——LLM 调用时看不到最新的 MCP 工具列表。顺序不是随意排的，每一道工序的位置由"被谁消费"决定。

3. **assemble_tool_pool 每轮动态组装：27 内置 + N 个 MCP**
   ```python
   def assemble_tool_pool() -> tuple[list[dict], dict]:
       tools = list(BUILTIN_TOOLS)     # 27 个内置工具（固定）
       handlers = dict(BUILTIN_HANDLERS)
       for server_name, mcp_client in mcp_clients.items():
           for tool_def in mcp_client.tools:
               prefixed = f"mcp__{safe_server}__{safe_tool}"
               tools.append({...})
               handlers[prefixed] = lambda ...: c.call_tool(t, kw)
       return tools, handlers
   ```
   每轮都重新组装——不是"启动时组装一次，之后复用"。因为 `mcp_clients` 可能在运行中变化（`connect_mcp` 连接新服务器），缓存的工具列表会漏掉新工具。s20 的 agent_loop 每轮开头都重新调用 `assemble_tool_pool()` 和 `assemble_system_prompt()`——代价是多花一点序列化时间，换取了工具池的实时性。

4. **两层计划 + 两种 delegation：s20 的协作体系**
   ```
   两层计划:
     todo_write (s05):   内存列表 / 当前会话 / 无依赖 / 你自己的步骤
     task graph (s12):   磁盘持久化 / 跨会话 / blockedBy DAG / 多 Agent 共享

   两种 delegation:
     task (s06):         一次性子 Agent / 独立上下文 / 只返回最终摘要
     spawn_teammate (s15): 持久队友线程 / 收件箱通信 / idle轮询 / auto-claim
   ```
   s05 的 todo_write 和 s12 的 task graph 不冲突——前者管"我现在做什么"，后者管"项目应该按什么顺序做"。s06 的 subagent 和 s15 的 teammate 也不冲突——前者是临时外包，后者是长期同事。s20 同时保留了这两套体系，因为真实场景中两者都需要。

5. **PreToolUse hooks + permission：s20 的权限为什么不是"写死在工具里"**
   ```python
   # s02-s04: permission check 是独立的 hook，不是工具代码的一部分
   blocked = trigger_hooks("PreToolUse", block)
   if blocked:
       results.append({"type": "tool_result",
                       "tool_use_id": block.id,
                       "content": str(blocked)})
       continue  # 跳过工具执行

   # 工具代码不感知权限
   handler = handlers.get(block.name)
   output = handler(**block.input)  # 工具只关心"怎么执行"
   ```
   如果把权限检查写在 `run_bash` 里——每次加新工具都要记得复制权限逻辑，容易漏。s20 把权限放在 `PreToolUse` hook 里，和工具代码解耦。`register_hook("PreToolUse", permission_hook)` + `register_hook("PreToolUse", log_hook)`——加一个新的安全检查只需要注册一个新 hook，不改任何工具代码。

6. **压缩管道的四层：为什么 L1-L4 的顺序不能换？**
   ```python
   def prepare_context(messages):
       messages[:] = tool_result_budget(messages)  # L3: 先压当前消息的大输出
       messages[:] = snip_compact(messages)        # L1: 消息数太多就裁中间
       messages[:] = micro_compact(messages)       # L2: 旧的 tool_result 截断
       if estimate_size(messages) > CONTEXT_LIMIT:
           messages[:] = compact_history(messages)  # L4: 最后才请 LLM 摘要
   ```
   L3 在 L1 之前——因为 `tool_result_budget` 只处理最后一条 user 消息中的超大 tool_result，它操作的是"当前上下文"。L1 → L2 的顺序是有意为之——先做无损的 snip（保留头尾 3+47），再做有损的 micro（截断旧结果）。L4 是最后手段——前面的都压不下来了，才调用 LLM 生成摘要。如果把 L4 放在前面，LLM 会做更多次摘要调用，token 成本更高。

7. **s19 → s20：不是"加功能"，是"合回来"**
   | 补回的机制 | 在循环中的位置 | 说明 |
   |-----------|--------------|------|
   | s03 permission + s04 hooks | PreToolUse / PostToolUse / Stop 钩子点 | 权限不写死在工具里 |
   | s05 todo_write + reminder | LLM 前注入提醒 + 循环中计数 | 与 s12 task graph 并存 |
   | s06 subagent | 工具分发中的一个 handler | task() 独立上下文 30 轮 |
   | s07 skills | system prompt 中 catalog | load_skill 按需加载 |
   | s08 compaction | LLM 前 L1-L4 管道 + compact 工具 + reactive compact | 上下文预算管理 |
   | s11 error recovery | LLM 调用层 with_retry + max_tokens + prompt_too_long | 三条恢复路径 |
   | s13 background tasks | should_run_background → start_bg → <task_notification> | 慢操作不阻塞 |
   | s14 cron scheduler | daemon thread + cron_autorun_loop | 定时自动执行 |

   s20 的工具从 s19 的 18 个扩展到 27 个（补回了 s05 的 todo_write、s06 的 task、s07 的 load_skill、s08 的 compact、s14 的 cron 三件套）。agent_loop 从"同步工具执行 + MCP 动态池"升级为"14 道工序的完整 harness"。但核心 `while True + LLM + tool_use + execute + messages.append` 完全没变——变的是循环周围的 harness。
