>*"没有计划的 Agent，做着做着就偏了"* -- todo_write 不给 Agent 增加执行能力，它增加的是规划能力。
>
>**Harness 层**: 规划 — 让 Agent 在动手之前先想清楚。

## 问题

给 Agent 一个复杂任务："把所有 Python 文件改成 snake_case 命名，然后跑测试，修好失败。"

Agent 开始干活，改了 3 个文件，跑了个测试，发现 2 个失败，开始修。修着修着，它忘了最初是要"改成 snake_case"，测试失败把注意力全吸走了。

对话越长越严重：工具结果不断填满上下文，系统提示的影响力被稀释。一个 10 步重构，做完 1-3 步就开始即兴发挥，因为 4-10 步已经被挤出注意力了。

Agent 缺的不是执行能力——bash、read、write 它都有。它缺的是**记住自己该做什么**的能力。

## 解决方案

```
+---------+      +-------+      +------------------+
|  User   | ---> |  LLM  | ---> | TOOL_HANDLERS    |
| prompt  |      |       |      |  bash            |
+---------+      +---+---+      |  read_file       |
                       ^         |  write_file      |
                       | result  |  edit_file       |
                       +---------+  glob            |
                                     todo_write ← NEW
                                  +------------------+
                                       |
                        in-memory CURRENT_TODOS
                                       |
                       if rounds_since_todo >= 3:
                         inject <reminder>
```

s04 的钩子系统完全保留。新增的是一个**纯规划工具**——`todo_write` 不能读文件、不能跑命令，只管内存中的 `CURRENT_TODOS` 列表。dispatch 机制不变，新工具自动走 `TOOL_HANDLERS[block.name]` 分发。

为了防止模型忘记使用这个工具，循环里加了一个计数器：连续 3 轮没调用 `todo_write`，就自动注入一条 `<reminder>` 消息。

s05_todo_write.py - 规划工具（TodoWrite）

s04 让 Agent 安全地执行操作了。但给它一个复杂任务，它是一上来就动手，还是先列个计划？

s05 的回答：给 Agent 一个 todo_write 工具，让它在动手之前先理清思路。

    # todo_write 本身不做任何实际工作
    def run_todo_write(todos: list) -> str:
        global CURRENT_TODOS
        # 校验：每个 todo 必须含 content 和 status
        for i, t in enumerate(todos):
            if t["status"] not in ("pending", "in_progress", "completed"):
                return f"Error: invalid status '{t['status']}'"
        CURRENT_TODOS = todos
        # 终端打印任务列表，不同状态用不同图标
        for t in CURRENT_TODOS:
            icon = {"pending": " ", "in_progress": "▸", "completed": "✓"}[t["status"]]
            print(f"  [{icon}] {t['content']}")
        return f"Updated {len(CURRENT_TODOS)} tasks"

    # 工具定义和其他 5 个一起加入 TOOLS 数组 + TOOL_HANDLERS 映射
    TOOLS = [
        ...bash, read_file, write_file, edit_file, glob...  # s02 的 5 个
        {"name": "todo_write", ...}                          # s05 新增
    ]

    TOOL_HANDLERS["todo_write"] = run_todo_write  # dispatch map 加一行

Agent 收到任务后的典型流程：
    1. 调 todo_write → 列出所有步骤（全 pending）
    2. 做一个步骤 → 把状态改成 in_progress
    3. 做完 → 改成 completed
    4. 看下一个 pending → 继续

## 核心设计模式解读

1. **为什么需要规划工具？LLM 自己不会想吗？**
   LLM 会"想"，但它的"想"受限于上下文窗口。做第 5 步的时候，第 1-3 步的结果可能已经被挤出去了。更关键的是，它没有持久化的"任务状态"——这轮 done 了、下轮又想起来，纯靠模型的模糊记忆。`todo_write` 把任务列表外化到内存中，模型每次都能看到自己规划了什么、做完了几步、还剩几步。这是从"靠记忆"到"靠系统"的跨越。

2. **todo_write 是一个"对模型自己说话"的工具**
   回顾 s02：加工具是为了扩展 Agent 能触达的边界——读文件、写文件、跑命令。`todo_write` 不触达任何外部世界。它改变的是模型自己的行为——让它更有条理、更少跑偏。这是一种**元工具**（meta-tool）：工具的产出不是文件或命令结果，而是模型对自己行为的约束。

3. **Nag 提醒为什么需要？**
   系统提示说"先规划再执行"，但对话进行到第 10 轮时，系统提示的影响力已经被后续消息稀释了。模型可能忙于处理工具结果，忘了更新 todos。Nag 提醒在模型"忘记"时主动干预，把注意力拉回来。3 轮是一个教学友好的阈值——太短会打断正常流程，太长则模型可能已经跑偏很远。生产环境（CC）没有固定的"3 轮"逻辑，而是用更精细的 nudge 机制（如全部完成但没有 verification 项时追加提醒）。

4. **dispatch map 模式再次验证了自己的价值**
   s02 说"加工具不需要改循环"。s05 用 `todo_write` 再次证明了这一点。新增 1 个工具 = 写 1 个 handler 函数 + TOOLS 加 1 条定义 + TOOL_HANDLERS 加 1 行映射。循环只加了一个计数器和一条 reminder 注入，工具分发路径完全没变。s02 的架构决策在 s05 得到了回报。

5. **任务状态不是装饰——它是模型的行为锚点**
   `pending` → `in_progress` → `completed` 这三个状态不只是给人类看的。模型读到 `[▸] refactor auth.py` 就知道"这是我正在做的事"，读到 `[✓] add type hints` 就知道"这个已经做完了"。状态的流转给了模型一个清晰的"进度感"，减少了重复劳动和遗漏。这是结构化输出对 LLM 行为的正向约束。
