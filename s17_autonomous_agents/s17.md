> *"自己看板，自己认领"* — 空闲时轮询，有活就干。
>
> **Harness 层**: 自治 — 队友自组织，不依赖 Lead 分配。

```python
s17_autonomous_agents/code.py - 带 idle_poll + scan_unclaimed + 自动认领的 Agent

s16 的队友能通信、能握手关机。但每个队友等 Lead 分配任务——如果任务看板上有
10 个未认领任务，Lead 得手动 assign 10 次。这不能扩展。
队友应该自己看任务看板，发现没人做的任务就认领，做完再找下一个。

s17 的回答：给队友装一双"眼睛"。idle_poll 每 5 秒轮询一次——先看收件箱有没有消息，

Lead 只需要创建任务和启动队友，不用手动分配。

s16 手动分配 vs s17 自动认领:
  s16 (领导驱动): Lead → create_task → spawn_teammate → manual assign → teammate works
  s17 (自组织):   Lead → create_tasks → spawn_teammates → teammates idle_poll → auto-claim → work

三阶段生命周期：
  WORK:     inbox → LLM → tools → (tool_use? → 循环) → (LLM停下? → IDLE)
  IDLE:     每 5s 轮询 → inbox有消息? → WORK / 任务板有未认领? → claim → WORK / 60s超时? → SHUTDOWN
```

### 💡 核心设计模式解读：

1. **s16 领导驱动 vs s17 自组织：从 manual assign 到 auto-claim**
   ```
   s16 (领导驱动): Lead → spawn_teammate("alice") + send_message("做 schema")
                   Lead 必须记得 alice 在做什么、bob 在做什么、谁有空
                   10 个任务 = 10 次手动分配

   s17 (自组织):   Lead → create_tasks × 3 + spawn_teammates × 2
                   alice IDLE → scan → "schema" → claim → WORK
                   bob IDLE → scan → "API" → claim → WORK
                   10 个任务 = 0 次手动分配
   ```
   s16 的 Lead 像一个"微管理"老板——给每个下属分配具体任务。s17 的 Lead 像一个"目标"管理者——放了任务板就走了，队友自己看板自己领。这不仅是"省了手动分配"，更是"队友知道自己的完成速度，Lead 不用追踪所有人的进度"。

2. **idle_poll 的两个优先级：为什么 inbox 必须在任务板前面？**
   ```python
   def idle_poll(agent_name, messages, name, role):
       for _ in range(12):  # 60s / 5s = 12 轮
           time.sleep(5)

           # 优先级 1: 检查收件箱
           inbox = BUS.read_inbox(agent_name)
           if inbox:
               for msg in inbox:
                   if msg.get("type") == "shutdown_request":
                       # 立即处理 shutdown，不等到下一轮 WORK
                       BUS.send(name, "lead", "shutdown_response", ...)
                       return "shutdown"
               messages.append(...)  # 普通消息→注入
               return "work"

           # 优先级 2: 扫描任务板（只有 inbox 为空时才进行）
           unclaimed = scan_unclaimed_tasks()
           if unclaimed:
               result = claim_task(task["id"], agent_name)
               if "Claimed" in result:
                   return "work"
       return "timeout"
   ```
   shutdown_request 如果在任务板后面，队友可能会在 IDLE 第 1 轮 claim 了一个任务进入 WORK，然后在 WORK 的 10 轮循环中才看到 shutdown。但如果 shutdown 很紧急，10 轮可能太久。inbox 优先保证了协议消息的时效性——"停下手头一切"的消息（shutdown）不会被"找活干"的动作延迟。

3. **scan_unclaimed_tasks 的三个条件 + can_start：依赖解锁的正确判断**
   ```python
   def scan_unclaimed_tasks():
       for f in sorted(TASKS_DIR.glob("task_*.json")):
           task = json.loads(f.read_text())
           if (task.get("status") == "pending"     # ① 待认领
                   and not task.get("owner")        # ② 无人持有
                   and can_start(task["id"])):      # ③ 依赖已满足
               unclaimed.append(task)
   ```
   三个条件的组合覆盖了"可认领"的完整语义：(1) pending——已经完成或进行中的不能认领；(2) 无 owner——alice 在做的任务，bob 不能抢；(3) can_start——如果依赖的 schema 还没完成，API 路由任务就不能开始。注意 `can_start` 是 s12 就有的函数，s17 重用了——`blockedBy` 任务必须存在且 status=completed。

4. **claim_task 的 owner 检查：教学版的"软锁"**
   ```python
   def claim_task(task_id, owner="agent"):
       if task.status != "pending":
           return "..."
       if task.owner:                                  # s17 新增：拒绝已持有
           return f"Task {task_id} already owned by {task.owner}"
       if not can_start(task_id):
           return "..."
       task.owner = owner
       task.status = "in_progress"
       save_task(task)
   ```
   教学版没有文件锁——如果 alice 和 bob 同时 `claim_task("task_schema")`，两人都可能通过 owner 检查（都看到 `owner=None`），然后后写者覆盖前写者。但在实际运行中，队友的 5 秒轮询间隔 + task.owner 检查已经让这种竞态极难触发（两个队友必须在完全相同的 5 秒窗口内同时读同一个文件）。CC 用 proper-lockfile 保证原子性，教学版用"概率性正确"换取代码简洁。

5. **Identity re-injection：上下文压缩后的"我是谁"提醒**
   ```python
   # s17 新增：在每次 WORK 阶段开始时检查
   if len(messages) <= 3:
       messages.insert(0, {"role": "user",
           "content": f"<identity>You are '{name}', role: {role}. "
                      f"Continue your work.</identity>"})
   ```
   如果 messages 只剩 3 条，说明发生了上下文压缩（s08 的 autoCompact 将所有历史压缩成了一条摘要）。压缩后的摘要丢失了 system prompt 中的身份信息，队友可能"忘记"自己是 alice，以为自己是 Lead。identity re-injection 是一个便宜的补救——不需要重新走 prompt 组装，只在 user 消息前插入一个身份提醒。CC 的真实现实的 compaction 会保留 system prompt，教学版需要手动处理。

6. **WORK/IDLE 双层循环：为什么不能把 IDLE 放在 WORK 里面？**
   ```python
   # 外层: WORK/IDLE 交替
   while True:
       # 内层: WORK 阶段（最多 10 轮 LLM）
       for _ in range(10):
           inbox_check → LLM → tools
           if stop_reason != "tool_use":
               break  # LLM 停下来了 → 去 IDLE
       # IDLE 阶段
       idle_result = idle_poll(...)
       if idle_result in ("shutdown", "timeout"):
           break
   ```
   如果把 IDLE 放在 WORK 的每轮循环中（工-等-工-等），会导致：每轮 LLM 调用后都要等 5 秒。pip install 的数据还没回来，但 LLM 已经想要下一步工具调用了——白等 5 秒。双层结构让 WORK 阶段保持紧凑（LLM 连续调用最多 10 次），只有 LLM 主动说"我完成了"才进入 IDLE 等待新任务。

7. **s16 → s17：加了 2 个核心函数 + 3 个队友工具 + 1 个新阶段，Lead 端几乎不变**
   | 新增 | 说明 |
   |------|------|
   | `scan_unclaimed_tasks` | 扫描任务板找到可认领任务（3 条件：pending+无owner+依赖满足） |
   | `idle_poll` | IDLE 阶段核心轮询（60s，两优先级：inbox→任务板） |
   | `claim_task` 新增 owner 检查 | 拒绝已有 owner 的任务（软锁） |
   | Identity re-injection | 上下文压缩后重新注入身份（`len(messages) <= 3`） |
   | 队友工具 +3 | list_tasks / claim_task / complete_task（5→8） |
   | 三阶段生命周期 | WORK(10轮) → IDLE(idle_poll) → SHUTDOWN(summary) |
   | `_run_list_tasks` / `_run_claim_task` / `_run_complete_task` | 队友专用闭包（owner=队友名称） |

   移除：s17 删除了后台任务系统（`should_run_background`/`start_background_task`/`collect_background_results`）和 cron 调度器，agent_loop 回归到最简单的同步工具执行。所有异步能力（inbox 轮询、任务认领）集中在队友线程的 idle_poll 中，Lead 主循环保持简洁。
