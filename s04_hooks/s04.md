>*"挂在循环上, 不写进循环里"* -- hook 在工具执行前后注入扩展逻辑，循环只负责调用 trigger_hooks()。
>
>**Harness 层**: hook — 扩展点不侵入循环。

## 问题

s03 的 Agent 有权限检查了。但 `check_permission()` 是硬编码在循环里的。每次加一个新需求——"记录每次 bash 调用"、"操作后自动 git add"、"大文件输出告警"——都要修改 `agent_loop` 函数。

很快循环就变成了这样：

```python
def agent_loop(messages):
    while True:
        # ... LLM call ...
        for block in response.content:
            if block.type == "tool_use":
                log_to_file(block)          # 加一行
                check_permission(block)     # 加一行
                notify_slack(block)         # 又加一行
                output = execute(block)
                auto_git_add(block)         # 再加一行
                # ... 循环很快就认不出来了
```

你想扩展的是 Agent 的行为，但你改的却是循环本身。循环应该是一个稳定的核心，扩展应该挂在外面。

## 解决方案

```
  User types query / 用户输入
       │
       ▼
  ┌──────────────────┐
  │ UserPromptSubmit │ ── trigger_hooks() before LLM
  └────────┬─────────┘
           ▼
  ┌────────────┐     ┌─────────────────────────────┐
  │  messages  │────▶│  LLM (stop_reason=tool_use?)│
  └────────────┘     │   No ──▶ Stop hooks ──▶ exit │
                     │   Yes ──▶ tool_use block ──┐ │
                     └────────────────────────────┘ │
                                                    ▼
                                          ┌──────────────────┐
                                          │ trigger_hooks()   │
                                          │  PreToolUse:      │
                                          │   permission_hook │
                                          │   log_hook        │
                                          └───────┬──────────┘
                                                  │ (not blocked)
                                          ┌───────▼──────────┐
                                          │ TOOL_HANDLERS[x]  │
                                          └───────┬──────────┘
                                                  │
                                          ┌───────▼──────────┐
                                          │ trigger_hooks()   │
                                          │  PostToolUse:     │
                                          │   large_output    │
                                          └───────┬──────────┘
                                                  │
                                          results ──▶ back to messages
```

s03 的权限逻辑完全保留，但它不再直接写在循环里了。循环只调用 `trigger_hooks()`，由注册表决定跑什么。四个事件覆盖完整的 agent cycle：

| 事件 | 触发时机 | 典型用途 |
|------|---------|---------|
| UserPromptSubmit | 用户输入后、进入 LLM 前 | 输入验证、注入上下文 |
| PreToolUse | 工具执行前 | 权限检查、日志记录 |
| PostToolUse | 工具执行后 | 副作用处理、大输出告警 |
| Stop | 循环即将退出时 | 收尾清理、统计汇总 |

```python
s04_hooks.py - 钩子系统（Hook System）

s03 的 check_permission() 是硬编码在循环里的。s04 把它移到了钩子上。

钩子系统的核心只有两个函数：

    HOOKS = {"UserPromptSubmit": [], "PreToolUse": [], "PostToolUse": [], "Stop": []}

    def register_hook(event, callback):
        HOOKS[event].append(callback)  # 把回调函数绑到事件上

    def trigger_hooks(event, *args):
        for callback in HOOKS[event]:
            result = callback(*args)
            if result is not None:     # 返回值 ≠ None → 拦截/阻止
                return result
        return None

s03 的权限逻辑封装成 permission_hook，挂到 PreToolUse 事件上：

    def permission_hook(block):
        """PreToolUse: s03 的三道门逻辑合并为一个钩子。"""
        if block.name == "bash":
        for pattern in DENY_LIST:
            if pattern in block.input.get("command", ""):
                return "Permission denied by deny list"
        if block.name in ("write_file", "edit_file"):
            path = block.input.get("path", "")
            if not (WORKDIR / path).resolve().is_relative_to(WORKDIR):
                choice = input("   Allow? [y/N] ").strip().lower()
                if choice not in ("y", "yes"):
                    return "Permission denied by user"
        return None

    register_hook("PreToolUse", permission_hook)

循环里只改了一处。s03 直接调用 check_permission(block)，s04 改为触发钩子：

    # s03: if not check_permission(block): ...
    # s04:
    blocked = trigger_hooks("PreToolUse", block)
    if blocked:
        results.append({... "content": str(blocked)})
        continue

多出来的 PreToolUse 钩子（log_hook）、PostToolUse 钩子（large_output_hook）、
UserPromptSubmit 钩子（context_inject_hook）、Stop 钩子（summary_hook）都是
通过 register_hook() 添加的。循环代码不需要知道它们的存在。

加新功能 = 写一个回调函数 + register_hook() 一行注册。循环永远不动。
```

## 核心设计模式解读

1. **为什么要把扩展逻辑从循环里移出来？**
   s03 的 `check_permission()` 是循环的一部分。想加日志？改循环。想加大文件告警？改循环。每次改动都触碰最核心的代码路径，风险高、心智负担大。s04 把循环变成一个"事件发射器"——它只在关键节点调用 `trigger_hooks()`，具体逻辑由注册的回调函数决定。循环稳定了，扩展的点外移了。

2. **钩子的返回值语义**
   教学版用一个简单的约定：`return None` = 继续（放行），`return 非None字符串` = 阻止/拦截。这个设计刻意避免引入复杂的 HookResult 对象。PreToolUse 的非 None 返回值阻止工具执行，Stop 的非 None 返回值强制续跑（注入一条消息让模型继续）。一个返回值，两种语义，但都遵循"非 None = 有事发生"的直觉。

3. **四个事件覆盖了一个完整的 agent cycle**
   UserPromptSubmit（输入）→ PreToolUse（执行前）→ PostToolUse（执行后）→ Stop（退出），这四个锚点抓住了 agent 生命周期的所有关键阶段。生产环境的 CC 实际有 27 个事件（SessionStart、PreCompact、SubagentStop 等），但模式完全一样：事件名 + 回调列表 + trigger 调用。理解了四事件模型，就理解了整个钩子系统。

4. **s03 的 permission pipeline 和 s04 的 hook system 是什么关系？**
   不是替代，是封装。s03 的三道门逻辑没有消失，只是被装进了 `permission_hook` 这个回调函数里，然后通过 `register_hook("PreToolUse", permission_hook)` 挂上去。钩子系统提供的是"在哪里挂"的机制，权限逻辑提供的是"挂上去的是什么"。两个概念正交——你可以把权限钩子换成别的检查逻辑，也可以在 PreToolUse 上再挂 10 个其他钩子，循环代码都不需要改。

5. **Stop 钩子的"续跑"能力**
   Stop 钩子返回非 None 字符串时，循环不会退出——而是把返回值作为一条 user 消息注入 messages，然后 `continue` 回到循环顶部。这意味着钩子可以在 Agent 即将停止时说"等等，还有一件事"，强制模型再跑一轮。CC 用这个机制实现了 `stopHookActive` 防无限循环保护，教学版省略了这个，但核心思想是一致的：钩子可以改变控制流。
