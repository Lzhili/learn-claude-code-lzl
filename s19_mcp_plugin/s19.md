### 💡 核心设计模式解读：

1. **s18 手写工具 vs s19 MCP 插件：从写代码到接协议**
   ```
   s18 (手写工具):  需要 Jira API？→ 写 run_jira_search + run_jira_create → 注册到 TOOLS
       每加一个外部服务 = 写一套工具代码 + schema + handler
       Agent 的工具是完全由开发者管理的封闭集合

   s19 (协议接入):  Jira 提供 MCP Server → connect_mcp("jira") → 自动发现 tools/list
       → assemble_tool_pool → mcp__jira__search / mcp__jira__create 自动可用
       每加一个外部服务 = 实现 MCP Server（任意语言），Agent 即插即用
   ```
   MCP 的核心价值不是"工具更多了"，而是"工具的来源开放了"。s18 的工具是封闭生态——只有你写的代码。s19 的工具是开放生态——任何符合 MCP 协议的服务都能接入。

2. **MCPClient: 教学版的 mock 如何模拟真实 JSON-RPC？**
   ```python
   class MCPClient:
       def __init__(self, name):
           self.tools = []              # 模拟 tools/list 的返回
           self._handlers = {}           # 模拟 tools/call 的实现

       def register(self, tool_defs, handlers):
           """模拟 MCP tools/list 发现。"""
           self.tools = tool_defs

       def call_tool(self, tool_name, args):
           """模拟 MCP tools/call 调用。"""
           handler = self._handlers.get(tool_name)
           return handler(**args)  # 直接调用 Python 函数
   ```
   真实 MCP：Agent 启动子进程 → 通过 stdin/stdout 发送 JSON-RPC 请求 `{"method": "tools/list"}` → 子进程返回工具定义列表。教学版用 `register()` 一次性注册工具定义和 handler——把"进程间 JSON-RPC 通信"简化为了"内存函数调用"。代价是你看不到真实的进程管理和错误恢复，好处是不依赖外部进程就能跑完整流程。

3. **mcp__ 命名空间 + normalize_mcp_name: 为什么用双下划线而不是斜杠？**
   ```python
   _DISALLOWED_CHARS = re.compile(r'[^a-zA-Z0-9_-]')

   def normalize_mcp_name(name: str) -> str:
       return _DISALLOWED_CHARS.sub('_', name)

   # 组装时：
   prefixed = f"mcp__{safe_server}__{safe_tool}"
   # 结果: mcp__docs__search, mcp__deploy__trigger, mcp__deploy__status
   ```
   双下划线 `__` 是命名空间分隔符 ——`mcp__docs__search` = `mcp` 协议 + `docs` 服务器 + `search` 工具。用 `__` 而非 `/` 或 `.` 是因为工具名会作为 LLM 函数调用名传递，斜杠和点可能被某些序列化格式截断。`normalize_mcp_name` 保证所有组成部分（server名、tool名）都是安全的——非法字符替换为 `_`，防止注入或解析错误。这和 s18 的 `validate_worktree_name` 一样，是"边界清洗"模式——在外部数据进入系统前做一次规范化。

4. **assemble_tool_pool 的 lambda 闭包技巧：为什么 `c=mcp_client, t=tool_name` 是默认参数？**
   ```python
   for server_name, mcp_client in mcp_clients.items():
       for tool_def in mcp_client.tools:
           handlers[prefixed] = (
               lambda *, c=mcp_client, t=tool_def["name"], **kw:
                   c.call_tool(t, kw))
   ```
   这是 Python 闭包的经典陷阱。如果写成 `lambda *, **kw: mcp_client.call_tool(tool_def["name"], kw)`，所有 MCP tool 的 lambda 都会引用**循环最后一次迭代**的 `mcp_client` 和 `tool_def`——所有工具都会调用最后一个 server 的最后一个 tool。`c=mcp_client, t=tool_def["name"]` 将值绑定为**默认参数**，在定义时立即求值，避免了延迟绑定问题。

5. **无 prompt 缓存：为什么 s19 要去掉 s10 的缓存？**
   ```python
   # s10-s18: 有缓存
   system = get_system_prompt(context)  # json.dumps 后比哈希，不变就复用

   # s19: 无缓存
   def agent_loop(messages, context):
       tools, handlers = assemble_tool_pool()     # 每次重新构建
       system = assemble_system_prompt(context)    # 每次重新生成
       ...
       if any(b.name == "connect_mcp" ...):
           tools, handlers = assemble_tool_pool()  # MCP 连接后重建
           system = assemble_system_prompt(context)
   ```
   缓存的前提是"输入不变 → 输出不变"。s19 打破了这个前提——`connect_mcp` 会改变 `mcp_clients` 全局字典，导致 `assemble_tool_pool` 返回不同的工具列表。缓存的 system prompt 里的 tools 列表是旧的，LLM 看不到新连接的 MCP 工具。去掉缓存比"检测 MCP 变化后刷新缓存"更简单——教学版的工具池组装很快（只是合并两个 list），不值得维护缓存失效逻辑。

6. **MCP 工具标注 (readOnly)/(destructive)：文本标注 vs 真实权限**
   ```python
   # 教学版：在 description 中标注
   {"name": "search", "description": "Search documentation. (readOnly)", ...}
   {"name": "trigger", "description": "Trigger deployment. (destructive)", ...}
   ```
   教学版把权限信息放在文本描述中——LLM 看到 `(readOnly)` 就知道这个工具不需要确认，看到 `(destructive)` 就知道应该先问用户。但这只是提示，不是执行拦截。真实 CC 的 MCP 协议有独立的 tool annotations 结构体（不是嵌在 description 里），权限系统根据 annotation 决定是否弹出确认框。教学版的简化合理——因为 s03 的 permission 系统早已被后续章节省略了。

7. **s18 → s19：加了 1 个类 + 3 个函数 + 1 个工具，循环改为动态工具池**
   | 新增 | 说明 |
   |------|------|
   | `MCPClient` class | MCP 客户端（register + call_tool，mock tools/list + tools/call） |
   | `normalize_mcp_name` | 非法字符→下划线，保证 mcp__ 前缀安全 |
   | `_mock_server_docs` / `_mock_server_deploy` | 两个 mock MCP 服务器（docs + deploy） |
   | `MOCK_SERVERS` 字典 | 可用 MCP 服务器注册表 |
   | `connect_mcp` | 连接 MCP 服务器 → 创建客户端 → 注册到 mcp_clients |
   | `assemble_tool_pool` | 内置工具 + MCP 工具动态合并（lambda 默认参数闭包技巧） |
   | `connect_mcp` 工具 schema | Lead 的第 18 个工具 |
   | `BUILTIN_TOOLS` / `BUILTIN_HANDLERS` 重命名 | 从 `TOOLS` / `TOOL_HANDLERS` 改为前缀区分 |

   循环里的改动：agent_loop 从 `tools=TOOLS` 改为 `tools, handlers = assemble_tool_pool()`，connect_mcp 后重新组装。prompt 缓存被移除。MCP 工具仅 Lead 可用——队友仍使用 8 个固定工具，继承不受影响。
