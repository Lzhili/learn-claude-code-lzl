> *"prompt 是组装出来的, 不是写死的"* — 分段 + 按需拼接 + 缓存。
>
> **Harness 层**: 提示 — 运行时组装, 不硬编码。

```python
s10_system_prompt/code.py - 带运行时 prompt 组装 + 确定性缓存的 Agent

s01-s09 的 system prompt 都是一行硬编码:

    SYSTEM = f"You are a coding agent at {WORKDIR}. Use tools to solve tasks."

到 s09，Agent 已经有记忆、压缩、技能加载。prompt 越来越长，但结构是平的——
加能力 = 加字符串。换项目要重写，改一处可能影响全局。

s10 的回答：把 prompt 拆成独立片段（section），运行时根据状态按需拼接，缓存结果。

四个 section，两种加载策略:
  identity:  始终加载  → "你是谁"
  tools:     始终加载  → "你能用什么工具"（由 enabled_tools 状态驱动）
  workspace: 始终加载  → "你在哪里工作"
  memory:    条件加载  → "你该记住什么"（仅当 .memory/MEMORY.md 存在且非空）

架构图：
    ┌──────────────────────────────────────────┐
    │          PROMPT_SECTIONS（字典）           │
    │  identity:  "You are a coding agent..."   │  ← 始终加载
    │  tools:     "Available tools: bash..."    │  ← 始终加载
    │  workspace: f"Working dir: {WORKDIR}"     │  ← 始终加载
    │  memory:    "Relevant memories..."        │  ← 条件加载
    └────────────────┬─────────────────────────┘
                     │
    ┌────────────────▼─────────────────────────┐
    │         update_context(context, messages) │  ← 从文件系统检查真实状态
    │  {                                        │
    │    "memories": MEMORY.md 内容 or "",      │     .memory/MEMORY.md 存在?
    │    "enabled_tools": [...],                │     TOOL_HANDLERS 有哪些 key
    │    "workspace": str(WORKDIR),             │
    │  }                                        │
    └────────────────┬─────────────────────────┘
                     │
    ┌────────────────▼─────────────────────────┐
    │    get_system_prompt(context)             │  ← 带缓存
    │    key = json.dumps(context, ...)          │     确定性序列化
    │    if key == _last_key: return cached     │     context 不变 → 复用
    │    return assemble_system_prompt(context) │     context 变 → 重新拼接
    └────────────────┬─────────────────────────┘
                     │
    ┌────────────────▼─────────────────────────┐
    │    assemble_system_prompt(context)        │  ← 纯拼接
    │    sections = [identity, tools, workspace]│     始终加载 3 段
    │    if memories: sections.append(memories) │     条件加载 memory
    │    return "\n\n".join(sections)            │
    └──────────────────────────────────────────┘

核心洞察："s01-s09 的 SYSTEM 是'写死的一段话'，s10 把它变成了'组装出来的配置'。
         prompt 不是字符串，是状态。状态变了，prompt 自动变。状态不变，缓存直接用。"
```

### 💡 核心设计模式解读：

1. **为什么要拆分 system prompt？全写在一个字符串里出什么问题？**
   ```
   s09: SYSTEM = f"You are a coding agent at {WORKDIR}. Use tools. Memories available:\n{index}..."
   s10: PROMPT_SECTIONS = {"identity": ..., "tools": ..., "workspace": ..., "memory": ...}
        system = assemble_system_prompt(context)  # 运行时按需拼接
   ```
   s09 的 `SYSTEM` 是一个整体。加 `memory` 段落要拼接字符串，加 `skills` 段落要再拼接。对 prompt 的任何修改都要在同一个字符串上做手术。三个问题：(1) 修一处影响全局，(2) 换项目要重写全部，(3) 带全部内容浪费 token。s10 把 prompt 拆成分段字典后，每段独立维护、独立测试、按需加载。

2. **"按需加载"的依据：真实状态，不是关键词**
   ```python
   def update_context(context, messages):
       memories = ""
       if MEMORY_INDEX.exists():           # ← 真实文件系统检查
           content = MEMORY_INDEX.read_text().strip()
           if content:
               memories = content          # ← 读取真实内容
       return {"memories": memories, ...}
   ```
   memory section 是否加载，判断依据是 `.memory/MEMORY.md` 是否存在且非空，不是"用户消息里有没有提到记忆"。这个区分很重要——真实状态不会骗你，关键词匹配会。用户说"上次我记得你说过..."不代表真的有记忆文件；反过来，有记忆文件也不需要等用户提到才加载。这是 prompt 组装从"分析对话内容"到"检查系统状态"的关键跨越。

3. **确定性缓存：为什么用 `json.dumps` 而不是 `hash()`？**
   ```python
   _last_context_key = None
   _last_prompt = None

   def get_system_prompt(context: dict) -> str:
       global _last_context_key, _last_prompt
       key = json.dumps(context, sort_keys=True, ensure_ascii=False, default=str)
       if key == _last_context_key and _last_prompt:
           print("[cache hit] system prompt unchanged")
           return _last_prompt
       _last_context_key = key
       _last_prompt = assemble_system_prompt(context)
       return _last_prompt
   ```
   Python 的 `hash()` 不保证跨进程一致（PYTHONHASHSEED），且对 dict 不工作。`json.dumps` 是确定性的——同样的 context 字典，同样的 json 字符串，同样的缓存 key。这里缓存的是"字符串拼接"这个操作，不是 API 调用。真正的 CC 还通过 `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` 标记 API 层 prompt cache 的稳定/动态分界点——但教学版不需要，因为这里没有 API 层缓存。

4. **agent_loop 里 prompt 的刷新时机：每轮工具执行后**
   ```python
   def agent_loop(messages, context):
       system = get_system_prompt(context)       # 入口：获取初始 prompt
       while True:
           response = client.messages.create(..., system=system, ...)
           # ... 工具执行 ...
           messages.append({"role": "user", "content": results})
           context = update_context(context, messages)  # 重新检查文件系统
           system = get_system_prompt(context)          # 状态变了就刷新 prompt
   ```
   为什么不是每轮 LLM 调用前刷新？因为工具执行可能改变文件系统——Agent 可能写了新文件、删了旧文件。这些变化应该在下一轮被 prompt 反映出来。比如 Agent 在工具执行中首次创建了 `.memory/MEMORY.md`，下一轮的 system prompt 应该自动包含 memory section。

5. **四段 prompt 的语义结构：谁-能啥-在哪-记什么**
   ```
   identity:  你是谁      → "You are a coding agent. Act, don't explain."
   tools:     你能用什么   → "Available tools: bash, read_file, write_file." (从 TOOL_HANDLERS 推导)
   workspace: 你在哪      → f"Working directory: {WORKDIR}"
   memory:    你该记住什么 → (MEMORY.md 内容，条件加载)
   ```
   这不是随意分的。四段回答了 LLM 需要知道的四个基础问题。和 s07 的 skill loading（"知道有什么技能"vs"知道技能的具体内容"）类似，这里的 memory section 只带"记忆存在"的信号，不带全部记忆内容——完整内容通过 s09 的 `load_memories` 在消息层面注入。prompt 管"结构"，message 管"内容"。

6. **s09 → s10：加了 3 个函数 + 1 个字典，循环没膨胀**
   | 新增 | 说明 |
   |------|------|
   | `PROMPT_SECTIONS` | 4 段 prompt 片段字典 |
   | `assemble_system_prompt(context)` | 按状态拼接 prompt |
   | `get_system_prompt(context)` | 带确定性缓存的获取 |
   | `update_context(context, messages)` | 从文件系统推导 context |
   
   循环里的改动：`system = get_system_prompt(context)` 替代了 `system = build_system()`。`context` 从全局常量变成了每轮评估的动态状态。s09 在循环体内调 `build_system()` 重建字符串——每次都是新的，没有缓存；s10 只在 context 实际变化时才重新拼接。
