> *"按时间表生产工作, 调度与执行解耦"* — cron 调度 + 队列解耦 + 空闲交付。
>
> **Harness 层**: 调度 — 独立线程判断时间, 队列传递触发。

```python
s14_cron_scheduler/code.py - 带独立调度线程 + cron_queue + queue_processor 的 Agent

s13 的后台任务是"动作驱动"——agent 遇到 npm install 就丢后台，但所有操作仍然依赖
用户手动触发。你说一句，Agent 动一下。"每天早上 9 点跑测试"、"每 30 分钟检查 CI"——
这些周期性任务不该需要人每次来推。

s14 的回答：给 Agent 装一个闹钟。独立守护线程每秒轮询 cron 表达式，
到点了把任务塞进 cron_queue，queue_processor 在 Agent 空闲时自动交付。
用户不输入任何东西，Agent 也会在到点时自己跑起来。

四层模型：
  Layer 1 (Scheduler):      守护线程检查时间 → 触发匹配任务 → 写入 cron_queue
  Layer 2 (Queue):          cron_queue 解耦调度器与 agent 循环
  Layer 3 (Queue Processor): Agent 空闲 + 队列非空 → 自动启动 agent_loop
  Layer 4 (Consumer):       agent_loop 消费队列 → 注入 "[Scheduled] ..." 到user

架构图：
    ┌─────────────────────────────────────────────────┐
    │  启动时:                                         │
    │  load_durable_jobs()  ← .scheduled_tasks.json   │
    │  Thread(cron_scheduler_loop, daemon=True)        │  ← Layer 1
    │  Thread(queue_processor_loop, daemon=True)       │  ← Layer 3
    └────────────────────┬────────────────────────────┘
                         │
    ┌────────────────────▼────────────────────────────┐
    │  cron_scheduler_loop (独立守护线程, 1s 轮询)      │
    │                                                  │
    │  while True:                                     │
    │    time.sleep(1)                                 │
    │    for job in scheduled_jobs:                    │
    │      if cron_matches(job.cron, now):            │
    │        if 同一分钟未触发过:                        │
    │          cron_queue.append(job)  ← Layer 2       │
    │        if not job.recurring: 移除                │
    └────────────────────┬────────────────────────────┘
                         │ cron_queue（共享队列）
    ┌────────────────────▼────────────────────────────┐
    │  queue_processor_loop (守护线程, 0.2s 轮询)      │
    │                                                  │
    │  while True:                                     │
    │    if 队列空: continue                           │
    │    if agent正忙(agent_lock): continue            │
    │    run_agent_turn_locked()  ← 自动启动一轮对话    │
    └────────────────────┬────────────────────────────┘
                         │
    ┌────────────────────▼────────────────────────────┐
    │  agent_loop (Layer 4: Consumer)                  │
    │                                                  │
    │  fired = consume_cron_queue()  ← pop + clear     │
    │  for job in fired:                               │
    │    messages.append("[Scheduled] job.prompt")      │
    │  → LLM 调用 → 工具执行 → 结果返回                 │
    └─────────────────────────────────────────────────┘

核心洞察："s13 的后台任务是'你要做什么，慢的我帮你跑'。s14 的定时调度是
         '你不用说什么，到点我自己跑'。从被动响应到主动触发——
         cron_scheduler_loop 和 queue_processor_loop 两把锁
         (cron_lock + agent_lock) 把三个独立线程安全地串在一起。"
```

### 💡 核心设计模式解读：

1. **动作驱动 vs 时间驱动：s13 和 s14 的本质差异**
   ```
   s13 (动作驱动): 用户输入 → LLM 决定工具 → npm install 太慢 → 丢后台
       触发器 = 用户行为，后台任务是 agent 的"优化策略"

   s14 (时间驱动): cron 线程到点 → cron_queue.append → agent 空闲 → 自动执行
       触发器 = 时间流逝，定时任务是 agent 的"内置时钟"
   ```
   两者不冲突，一个 Agent 可以同时跑两套：遇到 `pip install` 走 s13 后台，每天早上 9 点走 s14 定时。s14 的 `execute_tool` 内部仍然调用 s13 的 `start_background_task`——定时触发的命令如果很慢，也会丢后台。

2. **四层解耦：为什么调度、队列、投递、消费必须分开？**
   ```python
   # Layer 1: Scheduler — 只管"时间到了没有"
   def cron_scheduler_loop():
       if cron_matches(job.cron, now):
           cron_queue.append(job)  # 写队列，不管谁消费

   # Layer 3: Queue Processor — 只管"agent 闲不闲"
   def queue_processor_loop():
       if has_cron_queue() and agent_lock.acquire(blocking=False):
           run_agent_turn_locked()  # agent 空闲才投递

   # Layer 4: Consumer — 只管"队列里有啥"
   fired = consume_cron_queue()  # pop + clear
   ```
   如果调度器直接调 `agent_loop`，会出现两个问题：(1) 用户正在输入时调度器抢跑了 agent_loop，导致状态冲突；(2) 调度器每秒 tick 一次，agent_loop 可能跑好几秒，tick 会堆积。四层模型中，`cron_queue` 是天然的缓冲——调度器只管写，不管什么时候被消费。

3. **cron_matches: DOM/DOW OR 语义为什么是标准？**
   ```python
   def cron_matches(cron_expr: str, dt: datetime) -> bool:
       # 分钟、小时、月份必须全部匹配
       if not (m and h and month_ok):
           return False
       # DOM 和 DOW：同时约束时 OR 语义（任一满足即可）
       dom_unconstrained = dom == "*"
       dow_unconstrained = dow == "*"
       if dom_unconstrained and dow_unconstrained:
           return True   # * * → 每天
       if dom_unconstrained:
           return dow_ok  # 只约束了星期
       if dow_unconstrained:
           return dom_ok  # 只约束了日期
       return dom_ok or dow_ok  # 都约束了 → OR
   ```
   这是 Unix cron 的标准行为。"0 0 1 * 1" = 每月 1 号 OR 每周一 00:00 触发，不是 AND。如果 AND 的话，"每月 1 号且是周一"一年也就一两次，基本用不到。OR 语义更实用：你可以在"月初"和"周一"两个时间点都触发，不用写两个 cron。

4. **_last_fired 与 minute_marker：防重复触发 + 跨天不断档**
   ```python
   minute_marker = now.strftime("%Y-%m-%d %H:%M")  # 日期感知标记
   if _last_fired.get(job.id) != minute_marker:
       cron_queue.append(job)
       _last_fired[job.id] = minute_marker
   ```
   为什么不用 `last_fired_minute` 整型（0-1439）？因为 scheduler 每秒 tick 一次，这一分钟的每一秒 `cron_matches` 都返回 True。用最简单的 `"HH:MM"` 可以防止同一分钟重复触发，但第二天同一时间 `"HH:MM"` 相同，`_last_fired` 还是昨天那个，匹配相等，不会再触发。`"%Y-%m-%d %H:%M"` 在"分钟内防抖"和"跨天不断档"之间取得了平衡。

5. **queue_processor 的双重检查 + agent_lock：为什么检查两次队列？**
   ```python
   def queue_processor_loop():
       while True:
           time.sleep(0.2)
           if not has_cron_queue():    # 检查1: 无锁快速判断
               continue
           if not agent_lock.acquire(blocking=False):  # agent 忙
               continue
           try:
               if not has_cron_queue():  # 检查2: 持锁后再次确认
                   continue
               run_agent_turn_locked()
           finally:
               agent_lock.release()
   ```
   检查 1 在持锁前——队列为空就跳过，不竞争锁。检查 2 在持锁后——从获取锁到真正执行之间可能被用户消费掉了。双重检查是一个非常经典的模式，在"加锁成本低但误判成本高"的场景下常见。

6. **validate_cron：在边界上拦截，而不是在循环中崩溃**
   ```python
   def schedule_job(cron, prompt, ...):
       err = validate_cron(cron)  # 注册时验证
       if err: return err

   def load_durable_jobs():
       err = validate_cron(job.cron)  # 加载时重新验证
       if err:
           print(f"skipping invalid job {job.id}: {err}")
           continue
   ```
   `validate_cron` 在两个入口调用：(1) 模型通过 `schedule_cron` 创建时做实时校验；(2) 从磁盘 `load_durable_jobs` 时重新校验——防止用户手动改了 JSON 文件。如果非法表达式漏进去，调度器每次 tick 都会卡在那个 job 上报错，等于一个坏任务拖垮整个定时系统。

7. **s13 → s14：加了 1 个数据类 + 7 个函数 + 1 个线程 + 3 个工具，循环多了 Layer 4 消费**
   | 新增 | 说明 |
   |------|------|
   | `CronJob` dataclass | 5 字段：id/cron/prompt/recurring/durable |
   | `_cron_field_matches` | 单字段匹配（*/步进/列表/范围/精确值） |
   | `cron_matches` | 5 字段 cron 表达式匹配（DOM/DOW OR 语义） |
   | `_validate_cron_field` / `validate_cron` | 字段级 + 表达式级双重验证 |
   | `save_durable_jobs` / `load_durable_jobs` | 持久化读写 `.scheduled_tasks.json` |
   | `schedule_job` / `cancel_job` | 注册/移除定时任务 |
   | `cron_scheduler_loop` | Layer 1: 独立守护线程，1s 轮询 |
   | `consume_cron_queue` / `has_cron_queue` | Layer 4: 队列消费接口 |
   | `queue_processor_loop` | Layer 3: agent 空闲时自动交付 |
   | `agent_lock` | 防止 queue_processor 与用户输入并发执行 |
   | 3 个工具 schema + 3 个 `run_*` handler | schedule_cron / list_crons / cancel_cron |

   循环里的改动：agent_loop 开头新增 `fired = consume_cron_queue()` → 注入 user 消息。另外 s14 抽取了 `run_agent_turn_locked` 包装函数，让 queue_processor 和用户输入走同一条调用路径，避免代码分叉。三个线程（scheduler / queue_processor / 主循环）通过 `cron_lock` + `agent_lock` 两把锁安全协作。
