> *"一个搞不定, 组队来"* — 文件收件箱 + 队友线程 + 收件箱注入。
>
> **Harness 层**: 团队 — 多 Agent 协作, 消息总线。

```python
s15_agent_teams/code.py - 带 MessageBus + spawn_teammate_thread + inbox 注入的 Agent

s06 的子 Agent 是"临时工"——叫来干一件事，干完把结论传回来，退出。没有持续通信能力，
没有收件箱，Lead 只能等它跑完。一个"重构后端"的任务涉及认证模块、数据库层、API 路由、

s15 的回答：把 Agent 变成"Lead + N 个 Teammate"。Lead 是团队领导者，负责分配任务；

        Lead 和 Teammate 各自跑自己的循环，通过收件箱异步通信。
```

### 💡 核心设计模式解读：

1. **s06 子 Agent vs s15 队友：临时工和同事的本质差异**
   ```
   s06 (临时工):   Lead 调用 task() → 子 Agent 启动 → 跑完回传结论 → 销毁
       通信 = 单向（子→Lead 一次），生命周期 = 用完即焚

   s15 (同事):     Lead spawn_teammate("alice") → alice 后台持续运行
       → Lead 通过 send_message 随时通信 → alice 收件箱检查 → 回复
       通信 = 双向 + 多次，生命周期 = 多轮持续（直到 10 轮或任务完成）
   ```
   s06 适用于"帮我查一下这个函数的定义"，s15 适用于"你负责整个认证模块，有问题通过 inbox 找我"。一个是被调用的函数，一个是协作的同事。

2. **MessageBus: 为什么用文件而不是内存队列？**
   ```python
   class MessageBus:
       def send(self, from_agent, to_agent, content, msg_type="message"):
           inbox = MAILBOX_DIR / f"{to_agent}.jsonl"
           with open(inbox, "a") as f:                # append 一行 JSON
               f.write(json.dumps(msg) + "\n")

       def read_inbox(self, agent):
           inbox = MAILBOX_DIR / f"{agent}.jsonl"
           msgs = [json.loads(line) for line in ...]  # 读全部行
           inbox.unlink()  # 消费语义：读完删除
           return msgs
   ```
   三个理由选择文件：(1) 跨线程可观察——`cat .mailboxes/alice.jsonl` 直接看 Alice 收件箱里有什么；(2) 简单——不需要 `queue.Queue` 的阻塞语义，队友线程自己决定什么时候读；(3) 与 CC 设计一致——真实 CC 也在 `~/.claude/teams/{team}/inboxes/` 用文件收件箱。教学版的 `read_inbox` 有竞态风险（read+unlink 非原子），但教学场景可接受。

3. **spawn_teammate_thread: 队友的简化世界**
   ```python
   sub_tools = [bash, read_file, write_file, send_message]  # 只有 4 个工具
   sub_handlers = {
       "bash": run_bash, "read_file": run_read, "write_file": run_write,
       "send_message": lambda to, content: (BUS.send(name, to, content), "Sent")[1],
   }
   for _ in range(10):  # 最多 10 轮
       inbox = BUS.read_inbox(name)
       if inbox:
           messages.append({"role": "user", "content": f"<inbox>{json.dumps(inbox)}</inbox>"})
       response = client.messages.create(
           model=MODEL, system=system,
           messages=messages[-20:],  # 只保留最近 20 条消息，防止上下文膨胀
           tools=sub_tools, max_tokens=8000)
   ```
   队友没有 `create_task`、`schedule_cron`、`spawn_teammate`——不能再派子任务、不能设定时、不能再组队。教学版的"队友权限最小化"防止了递归膨胀。`messages[-20:]` 是简化版的上下文管理：不搞 s08 的四层压缩，直接 tail 截断。

4. **收件箱注入的两条路径：Lead 的两种消费方式**
   ```python
   # 路径 A: check_inbox 工具——LLM 主动检查
   def run_check_inbox():
       msgs = BUS.read_inbox("lead")  # 读即消费
       return "\n".join(f"[{m['from']}] {m['content'][:200]}" for m in msgs)

   # 路径 B: 主循环结束后自动注入——不需要 LLM 主动请求
   inbox = BUS.read_inbox("lead")
   if inbox:
       history.append({"role": "user", "content": f"[Inbox]\n{inbox_text}"})
   ```
   路径 A 是 LLM 自觉检查——"我想知道 alice 干完了没"。路径 B 是被动投递——不管 LLM 想不想看，队友结果自动出现在下一轮对话里。教学版用路径 B，因为队友的 `BUS.send` 用的是 `"result"` 类型，Lead 应该自动看到。

5. **队友的 work→idle→summary 生命周期**
   ```python
   def run():
       for _ in range(10):  # 工作阶段：最多 10 轮
           inbox = BUS.read_inbox(name)           # 检查收件箱
           response = client.messages.create(...)  # LLM 调用
           if response.stop_reason != "tool_use":
               break                              # 模型主动停下
       # 收尾阶段：提取摘要 → 发给 Lead
       summary = "Done."
       for msg in reversed(messages):
           if msg["role"] == "assistant":
               summary = 最后一条文本回复
               break
       BUS.send(name, "lead", summary, "result")  # 自动汇报
   ```
   队友不会"悄无声息地死掉"。即使 10 轮用完，也会发一条 `"result"` 消息给 Lead："Done." 或最后的文本回复。Lead 不需要轮询"你还活着吗"，队友完成时自然会通知。

6. **两个收件箱注入点 + 一个消费语义的冲突**
   ```python
   # agent_loop 内: LLM 可能调用 check_inbox 工具 → read_inbox("lead") → 消费
   # 主循环结束后: 再次 read_inbox("lead") → 可能为空！
   inbox = BUS.read_inbox("lead")  # 如果 LLM 已经 check_inbox 过，这里拿不到
   if inbox:
       history.append(...)         # 可能永远不触发
   ```
   这是一个教学版的已知竞态：如果 LLM 在 agent_loop 内调用了 `check_inbox`，`read_inbox` 已经 unlink 了 `lead.jsonl`。主循环结束后的第二次 `read_inbox` 拿不到消息。真实 CC 的 `useInboxPoller` 用文件锁 + 标记位避免重复消费，教学版保留了这种"可能有微妙 race"的教学价值。

7. **s14 → s15：加了 1 个类 + 3 个函数 + 3 个工具 + 1 个注入点，循环不变**
   | 新增 | 说明 |
   |------|------|
   | `MessageBus` class | 文件邮箱系统（send=append JSONL, read_inbox=read+unlink） |
   | `MAILBOX_DIR` + `active_teammates` | 邮箱目录 + 队友注册表 |
   | `spawn_teammate_thread` | 后台线程创建独立 Agent（简化工具集 + 10 轮上限） |
   | `run_spawn_teammate` / `run_send_message` / `run_check_inbox` | 3 个新工具 handler |
   | 3 个工具 schema | spawn_teammate / send_message / check_inbox |
   | 主循环外 inbox 注入 | `BUS.read_inbox("lead")` → 队友结果注入 history |
   | 队友的 sub_tools / sub_handlers | 4 工具限制（bash/read/write/send_message） |

   循环里的改动：agent_loop 内部不变——工具分发、后台任务、cron 消费全保持原样。唯一新增的是主循环结束后的收件箱检查。队友线程跑的是完全独立的 agent 循环，不共享 messages 或 context。
